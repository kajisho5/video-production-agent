name: video-production-agent
description: Plan and produce a video from source files - trim silence, normalize loudness, subtitles, color, thumbnails, deliver for YouTube / conference / broadcast - with you (the chat model) as the reasoning step and every action validated, approved and recorded. Use when asked to edit, finish, clean up, prepare or deliver a video or recording, or to explain why the plan decided something. Runs locally through `video-agent`; no API key needed.

# video-production-agent

You are the brain; `video-agent` measures, validates, executes and records. Run it with `--json` and read the JSON. Never call ffmpeg or a skill directly for a production: go through the plan so every step has evidence and approval.

## The production loop

1. **Plan with a brief**
   `video-agent --json plan <files...> --profile <youtube|conference|broadcast|generic> --request "<the user's words>" --ai-brief --ai-model claude-code`
   Note `project` (the plan path), `decisions` and `ai_brief`.
2. **Answer the brief** (this is your reasoning). Read `ai_brief.inputs` (measured facts, each with an id), `ai_brief.context.allowed_intents` and `ai_brief.context.request_text`, follow `ai_brief.rules`, and write `answer.json`:
   `{"recommendations": [{"intent": "silence_cleanup", "asset_id": "<id from inputs.assets>", "statement": "<why, from the facts>", "confidence": 0.8, "evidence": ["<observation or event id>"], "params": {}}]}`
   Only allowed intents, only ids that appear in the inputs, no commands / paths / code. An empty list is a valid answer.
3. **Record the answer**
   `video-agent --json revise <project> --ai-recommendations answer.json --ai-model claude-code`
   Report `ai.accepted` and `ai.dropped` honestly; a dropped recommendation was not used.
4. **Show the plan and ask** — list the CONFIRM decisions (`video-agent --json explain <project>` gives reason and evidence). Approve only what the user approves, in their words:
   `video-agent --json approve <project> --decision <ids|all> --by "<user>"`; to refuse: `reject <project> --decision <id> --reason "..."` then `revise <project>`.
5. **Render and check**
   `video-agent --json render <project> --dry-run` first if the user wants to see the steps, then `video-agent --json render <project>`, then `video-agent --json check <output> --platform <profile>`.

Explicit requirements go in as `--set key=value` on plan or revise (e.g. `audio.loudness.target_lufs=-16`, `edit.trim_leading_silence=true`).

**Feedback scope (ADR-111).** Feedback is about this video unless the user says otherwise. Pass `--scope channel` (with the project's `--channel <name>`) or `--scope all_videos` on revise only when the user said so. If you think a correction should apply more widely but the user did not say so, pass `--scope-by ai`: the item is then only a candidate. To keep a correction for future videos, ask the user first, then run `video-agent preferences promote <project> --feedback <id> --by "<user>"` (add `--confirm-scope <scope>` for a candidate). Only `--set` keys are stored, and every promotion is a new store version. `plan --channel <name>` applies the channel's stored preferences (provenance PREFERENCE; they never waive a confirmation) and records the versions used. If quality drops, `preferences list` / `diff` / `rollback --to N` (add `--channel` for a channel store; the global store is the default). `video-agent corrections <project>` reports corrections per delivered minute; it is a report, so do not act on it by yourself.

**A brief in the user's words** ("60 s vertical, captions, -14 LUFS") goes in as `--brief "<the user's words>"` on plan. With `--ai-brief` the result's `brief.host_request` is yours to answer: keys from `host_request.context.allowed_keys` only, each with the exact `phrase` of the brief it comes from, values as `--set` takes them, and what no key expresses (a target length) under `unmapped`. Write `brief.json` (`{"requirements": [{"key": "edit.fit", "value": "9:16", "phrase": "vertical", "confidence": 0.9}], "unmapped": [{"phrase": "60 s", "reason": "no key for a target length"}]}`) and plan again with `--brief "<same words>" --brief-requirements brief.json --ai-model claude-code` (`video-agent --json brief "<words>" --brief-requirements brief.json` checks it without analysing media). Report `brief.accepted`, `brief.refused` (with reasons), `brief.overridden` (explicit `--set` wins) and `brief.unmapped` honestly; the `requirements.brief` decision and every change resting on your keys are CONFIRM for the user.

## When a skill is missing (handoff)

Every skill is optional; the plan uses the ones installed here. `plan --json` lists steps no installed skill can run under `handoff` (job, reason, which package provides it, how to install it); those steps are BLOCKED. Tell the user, and either install the skill (`/plugin install <skill>@velisa`, or `./install.sh`) and plan again, or — only if the user agrees and it is safe — do that job with another installed skill or a standard tool. Say plainly that such a step is outside the agent: no contract, no provenance, no approval record, no QA by the agent. Then verify its output with `video-agent --json check <file>`.

A job the agent has no adapter for at all (another package of the ecosystem owns it) is asked for with `--set job.<skill>=true`: `dubbing`, `still_image_edit`, `render_3d`, `html_scene_render`, `disc_author` (a DVD or Blu-ray with menus, a disc folder or an .iso: oncemore, ADR-094; the only disc job). The plan then carries a BLOCKED step for it and a handoff naming the package, its repository and its install command (`none yet` for a package that has not been released). Use it when the user asks for such a job, so the request is recorded and handed over instead of silently dropped. For `render_3d` (blender-skill) and `html_scene_render` (hyperframes-skill) the handoff also carries `contract`: the Skill's tool from a pinned contract, the arguments you gave with `--set job.render_3d.model=<3d file> job.render_3d.preset=<1080p|...> job.render_3d.transparent=true` or `job.html_scene_render.scene=<folder with index.html> job.html_scene_render.codec=<h264|vp9|prores>` (checked against the pin before analysis), what is still missing, and where the output goes next (ffmpeg-skill/overlay, or video-editing/concat). Run that tool with the user; the agent does not run it or import its output (ADR-080).

Speech enhancement through voice-enhance-skill (ADR-073) is opt-in on the audio path: `--set audio.production=true` plus `voice.isolate=true` (AI voice isolation, 48 kHz input), `voice.dereverb=true` and / or `voice.bleed_reduce=true` (with `audio.mix=true`, one mixed input per microphone). Every one is EXPERIMENTAL, so it always waits for confirmation; a missing engine blocks with voice-enhance-skill's own code and install line (nothing is downloaded).

Faces are blurred only when asked: `--set edit.redact_faces=true` (+ `edit.redact_faces.mode=blur|pixelate`, `.every` seconds between sampled frames, default 0.5; `.window` to split a long track). detection-skill measures face boxes and links them into rectangles (ADR-090); the plan proposes `video.redact_faces`, which always needs the user's approval, and each rectangle is blurred only while it was measured. Tell the user the detector can miss small, turned-away or briefly visible faces and that the rendered video must be checked before it is published; never say who a face belongs to. Without detection-skill or its YuNet model file the plan hands the measurement off.

The slide changes of a talk recording come from slide-sync-skill (ADR-091) only when asked: `--set slides.detect=true` (+ `slides.deck=<the speaker's deck>` to know which page is on screen in each slide; `slides.min_dwell` / `slides.threshold` when builds or a camera produce extra cuts). It is measured picture cuts, not an understanding of the slides: report a page only where the match gave one, and say "not matched" for a null page. Without slide-sync-skill the plan hands the measurement off.

A document that goes out with the video (a script, a report, slides) is verified by artifacts-skill (ADR-095) when asked: `--set document.verify=<file>` (+ `document.verify.preset=print-a4` and the other artifacts-skill presets). It runs without approval (read-only); a leftover placeholder ("TODO", "Lorem ipsum") fails QA and the job ends in REVIEW: tell the user which markers were found. Caption files are not taken (qc=true checks them).

Measured motion graphics come from remotion-ffmpeg-skill (ADR-093) only when asked: `--set remotion.comp=Captioned remotion.project=<the user's Remotion project>` (PeakPulse, Titled, BeatMontage, Karaoke and Pip too; `remotion.captions=<srt>`). The render always needs the user's approval; Jumpcut / Highlights (they cut the picture) and a different aspect are not taken. Say Remotion's licence once if the user is a company of more than 3 people.

A music bed comes from sound-design-skill (ADR-092) and is mixed by audio-production MIX, on the audio path only: `--set audio.production=true audio.mix=true bgm.library=<a sound-design library>` (the user's own files, imported with their licence) or `bgm.prompt="calm piano bed"` (generated by ACE-Step, only if the user installed it). The bed is the mix's last input: set its level with `audio.mix.levels` and duck it with `audio.mix.duck.input=<its index>` + `.amount_db`. The bed always needs the user's approval; say a library licence is "declared", never "cleared", pass on its credit, and say generated music should be listened to.

An overlay image is prepared by imagemagick-skill (ADR-077) only when the user gives its size: `--set edit.overlay=logo.png edit.overlay.prepare.width=320 edit.overlay.prepare.height=180` (both; `edit.overlay.prepare.mode=fit|fill|exact`, default fit), `edit.overlay.prepare.pad=none|<colour>` (+ `.gravity`) to pad a fit to exactly that canvas, `edit.overlay.prepare.strip=true` to remove GPS / EXIF first. Never choose a size or a colour yourself; ask. The user's file is never written; without imagemagick-skill the step is handed off (`npx imagemagick-skill`).

Dubbing through dubbing-skill (ADR-085) is opt-in: `--set dub.cues=<translated cues .srt|.vtt|.json> dub.lang=<BCP-47>` (the user supplies the translation; neither the agent nor the Skill translates), optional `dub.engine` / `dub.voice` / `dub.duck` / `dub.voice_gain` / `dub.max_overrun` / `dub.on_unfit` / `dub.source_cues`. A real person's voice only with `dub.reference` **and** `dub.consent` (their `dubbing/consent@1` record, from the user — never write, edit or fill one in for them). It always needs confirmation; a `CONSENT_REQUIRED` result is reported to the user and never retried. Carry the receipt's `obligations.credit` into the published description or credits.

Who spoke when comes from diarization-skill (ADR-086) only when asked: `--set speakers.diarize=true` (+ `speakers.num_speakers=N` when the user knows the count, or `speakers.min_speakers` / `speakers.max_speakers`). The result is anonymous turns (`SPEAKER_00`, ...): never write a name for one unless the user told you who it is. Without diarization-skill, or with its engine / gated pipeline not set up, the plan hands the measurement off with diarization-skill's own install steps. Add `speakers.assign=true` (ADR-096) when the user wants the subtitles to say who speaks: the transcript then carries the anonymous ids (transcription-skill merges the measured turns), and the cues read "SPEAKER_00: ...". Tell the user the ids are voices, not names.

Three more measurements run only when asked by name (roadmap step 33): `--set text.detect=true` reads the text on screen with detection-skill (OCR lines with their boxes; `text.every=<seconds>`, `text.lang=jpn+eng`, `text.min_score`), `--set shots.detect=true` measures the frame-accurate shot table with detection-skill (`shots.threshold`, `shots.min_shot_frames`), and `--set speech_regions.detect=true` measures speech regions with media-analysis-skill's voice-activity model. Each is a measurement only: it edits nothing and names no one. Without the Skill or its engine (Tesseract, PySceneDetect, the `vad` extra), the plan hands the measurement off with the install line. `--set transcript.find=<phrase>` (+ `transcript.find.fuzzy=0.5..1`, `transcript.find.context=0..10`) finds every timed hit of a phrase in the transcript with transcription-skill's `find`; it finds, it does not cut. `job.visual_detection` is gone; use `text.detect` for text and `edit.redact_faces` for faces.

Publishing through publish-skill (ADR-087) needs the QC gate: `--set qc=true publish.platform=<id> publish.title=…` (+ `publish.description` / `publish.tags` / `publish.privacy` / `publish.thumbnail=true` / `publish.captions=true` where the platform takes them). It always needs confirmation; render only runs publish-skill's offline plan and dry run and reports the confirmation token. Never run `video-agent publish` yourself: the upload is for the human to type (`video-agent deliver <artifact>`, then `video-agent publish <artifact> --confirm <token>`), once; an upload is never retried.

Cutting words you choose (ADR-109) is opt-in: plan with `--set edit.word_cut=true` (+ `edit.word_cut.pre_roll` / `.post_roll`, seconds, defaults 0.1 / 0.2). The brief's `context.word_cut.transcripts[].words` lists each transcript's words as `[index, text]`. Answer with intent `word_cut` and `params` holding exactly one of `keep_words` or `cut_words`: inclusive `[first_index, last_index]` pairs, sorted, not overlapping, citing the `transcript_id`. Never write seconds; the agent converts the indices (word times plus the rolls, clamped so a kept range never reaches a word that is cut). An invalid answer is refused (a KEEP `words.cut` decision with the reason in `params.refused`): fix the indices, do not guess. The cut always needs the user's approval; show them the words that go (`params.removed_words`: first index, last index and the words' text) and the seconds (`params.remove`).

To check a render by ear (ADR-110), plan with `--set verify.transcript=true` (+ `verify.transcript.unit=char` for Japanese or another script without spaces, `verify.transcript.language` / `.engine` / `.model`, `.min_confidence`). After the render, `qa.transcript_verification` lists, per deliverable, words the plan kept that were not heard (`missing`), words heard more often than planned (`duplicated`), words that were not planned (`unexpected`) and `low_confidence` spans, each with delivered seconds (and source seconds where they map). Give the user that list as places to listen to: it is not a verdict and changes nothing. A recogniser also mishears clean audio, so say so; never edit or re-render because of it without the user. Report each deliverable's own status: CHECK_HERE (its items and notes), CLEAN, or NOT_COMPARED (with the note why). NOT_RUN means no transcription-skill, so nothing was checked; a status ending in `_PARTIAL` means some deliverables were compared and the warnings name the ones that were not.

Which transcription-skill engine and model recognise the sources (ADR-113) is the user's explicit choice, never a brief's or a stored preference's: `--set transcribe.engine=<engine id>` (e.g. `qwen3_asr`, `speechcpp`), `transcribe.model=<model name>` (e.g. `parakeet-tdt-0.6b-v3`, `distil-large-v3.5`) and `transcribe.word_segmentation=dictionary` (Japanese dictionary words: needs `--language ja` and a requirement that measures word timings, such as `edit.word_cut` or `verify.transcript`). Each is sent only to a transcription-skill contract that declares it. Without them nothing changes. A plan that names them is refused before anything runs when the plan measures no transcript, when the installed contract does not declare the option, or when the Skill's own dry run refuses the request, for example a model's language limit (`language_unsupported` / `language_detection_unsupported`) or dictionary segmentation without Japanese or word timings. The refusal quotes the Skill's reason. An engine or model that is not installed is left to the analysis, which records it as before. The choices and what the Skill used are in `provenance.transcription_options`.

qc-skill can check two things the agent joins (ADR-112), only when the user asks: `--set qc.stinger=true` checks a stinger CONCAT's cut point on each deliverable (cover statement, opacity at the cut point; with `qc.stinger.max_cut_frame_difference=<0..255>` also each delivered cut frame), and `qc.loop_seam.max_click_ratio` / `.max_level_diff_db` / `.max_band_diff_db` (the last two with `.window_sec`) check the seams of a library bed (`bgm.library`) that library-pick looped. None of these limits has a default: ask the user for one, do not pick it (qc-skill's docs give starting points: a cut frame difference around 2-5 for textured graphics in a lossy delivery after measuring their own; click ratio about 3, level 1.5 dB and band 6 dB with a 1 s window). Findings are QA items (layer `qc`): a FAIL keeps the deliverable from final, UNKNOWN and a check that could not run are WARN with the reason. Report them; never re-edit or re-render because of them without the user.

A thumbnail can carry more than one text and a logo (ADR-088): `thumbnail.color`, `thumbnail.text2` .. `thumbnail.text4` (each with `.position` / `.font_size` / `.color`) and `thumbnail.logo=<png|jpg>` (+ `.logo.position` top-left | top-right | bottom-left | bottom-right, `.logo.width`, `.logo.margin`, `.logo.opacity`); they are rendered as one thumbnail-skill ThumbnailDocument.

Files for Premiere / Resolve (ADR-089): `--set delivery.timeline=otio delivery.nle=export` (or `conform`; `delivery.nle.formats=otio,fcp7,edl,srt`) hands the executed project IR to nle-bridge-skill; pass on every warning it reports (what a format does not carry). When the editor sends the timeline back (OTIO / FCP7 XML / EDL), `video-agent revise <project> --editor-timeline <file>` (ADR-098) turns its changed cuts into CONFIRM `timeline.editor_cut` decisions of the next version: show the user the diff and the warnings (gaps closed, audio-only edits and effects not read back) before approving.

## Offloading a camera card (ingest-skill)

A card or recorder folder is planned on its own: `video-agent --json plan /Volumes/CARD_A --set ingest.dest=/Volumes/SSD1/Footage --set ingest.dest=/Volumes/SSD2/Footage --set ingest.project=2026-10-30_event` (optional `ingest.hash=xxh64`, `ingest.name_by=reel`, `ingest.reel=A001`). Name every destination the user gave you; never pick one yourself (each must be a mounted directory). The plan copies nothing: it shows ingest-skill's dry run and the card's inventory and one `ingest.offload` decision that is always CONFIRM. Ask the user, then `video-agent approve <plan> --decision <id>` and `video-agent render <plan>`. Report from `execution.offload`: say "verified" only when the status is COMPLETED; otherwise name the error `kind` (CONFLICT, PARTIAL, COPY_FAILED, HISTORY_DAMAGED, ...) and each destination from `details.destinations` (a PARTIAL keeps the complete drives listed under `details.complete`). Warn when the plan says two destinations are on one volume. The verified copies become assets with `ingest_clip` observations; plan the edit on those files next.

## Exit codes

0 done / 2 validation errors / 3 BLOCKED / 4 waiting for approval / 5 QA FAIL (revise: no new version) / 1 other. Exit 4 means ask the user, not retry with approval.

## Report it honestly

- "Done" only when render completed and QA passed; quote QA WARN / FAIL items.
- A measurement that is missing is **unknown**, not zero (e.g. loudness not measured).
- Say which decisions you recommended (AI_GENERATED) and that policy, not you, set their risk and approval.
- `video-agent doctor --json` when a skill is MISSING / DEGRADED: name it, do not work around it.
