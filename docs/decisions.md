# Architecture Decision Records

## ADR-001 ffmpeg-skill はプロセス境界で使う（ライブラリ import しない）
- 事実: `_common.STATE` がプロセスグローバル、`die()` が `sys.exit`、各スクリプトが兄弟を subprocess 起動する設計。
- 決定: `FfmpegSkillAdapter` が `python3 <skill>/scripts/<name>.py ... --json` を起動し、stdout JSON と終了コードを契約とする。
- 帰結: 並列実行・タイムアウト・キャンセルは Agent 側で制御できる。バージョンは `package.json` で固定（0.8.4 ≤ v < 0.9）。

## ADR-002 Phase 1 では `render.py` の project.json を使わない
- 事実: 固定ステージ順、スキーマ検証なし、`check` FAIL でも exit 0、dry-run でダミー probe。
- 決定: Agent 自身の Project IR + compiler を持ち、個別スクリプトを順に呼ぶ。
- 将来: IR → render project への lowering adapter は追加可能。
- 改訂（ADR-052）: 編集タイムラインの書き出し（`render.py --export-timeline`）に限り、adapter が IR の cut list から書いた最小の project.json（clips と `"transition": {"type": "none"}` だけ）を render.py に渡す。render.py でメディアを render することは引き続きしない。

## ADR-003 Agent 側の ffmpeg 直接呼び出しは機能検出のみ
- `-version / -encoders / -decoders / -filters` と `fc-list`。メディア処理は一切しない。

## ADR-004 出力パスは常に Agent の workspace、入力は allowed roots
- ffmpeg-skill は `-y` 固定で入出力同一パスの保護がないため、`PathPolicy` で強制。source は読み取りのみ。

## ADR-005 Phase 1 は AI プロバイダ無しで完全動作
- 自然言語は「曖昧さのないキーワード」のみ USER requirement に変換。それ以外は `--set key=value` で明示。
- `providers/` は NullProvider のみ。将来の抽出は provenance=AI_GENERATED として別扱い。

## ADR-006 Observation / Inference / Decision を別型にし、Inference は evidence 必須
- validator が evidence 参照の存在を検査。観測値は上書きされない。

## ADR-007 risk と approval を confidence から独立させる
- 先頭/末尾の技術的無音: LOW/AUTO（conference は CONFIRM）。中間無音: Phase 1 は提案しない（keep）。意味的削除: HIGH/CONFIRM、conference は BLOCK_UNLESS_EXPLICIT（constraint）。

## ADR-008 Recovery は有限（既定 2 試行）、QA FAIL は Recovery ではなく Revision
- 分類表 `execution/recovery.py`。QA FAIL の artifact は `working` に留まり `candidate` に昇格しない。

## ADR-009 conference の master ターゲットは Phase 1 では platform=custom
- 理由: broadcast 検査は -23 LUFS を要求し、web 向け -16 LUFS とターゲット別ラウドネスが必要（Phase 2 で per-target audio op を導入）。QA が実際にこの不整合を検出したため修正。

## ADR-010 PathPolicy が保証するものと保証しないもの（Phase 1 監査より）
- 保証する: 出力は常に `<workspace>/jobs/<id>/` 配下、出力パス = 入力パスは拒否、シェルを経由しない argv、catalog に無いフラグは拒否。
- 保証しない: 「読める入力」の制限。allowed root は入力パスの親ディレクトリから導出されるため、ユーザが指定したパス（シンボリックリンク先を含む）は常に読める。独立した `--allowed-input` 設定は Phase 2。

## ADR-011 子プロセスはプロセスグループで起動し、タイムアウト・割り込み時はグループごと kill する
- 事実: ffmpeg-skill のスクリプトは ffmpeg を孫プロセスとして起動する。`subprocess.run(timeout=)` はスクリプトだけを kill し、ffmpeg は出力ファイルを書き続けた（監査で再現）。
- 決定: POSIX は `start_new_session` + `killpg(SIGKILL)`、Windows は `CREATE_NEW_PROCESS_GROUP` + `taskkill /T`。失敗した試行の出力ファイルは削除してから再試行する。SIGINT は Executor が CANCELLED に変換し、Service は job / IR / provenance を必ず保存する。

## ADR-012 analysis.strategy は「実際に行った解析」を記録する
- Phase 1 は全ファイルの silence / loudness 解析しか無いので `FULL_ANALYSIS` を記録し、`budget.enforced=false` を明示する。プロファイルの要求値は `budget.requested_strategy` に残す。

## ADR-013 REJECTED 決定は実行不可、operation id は決定論的
- validator は REJECTED 決定を参照する operation / delivery target を error にし、render は実行しない（監査時点では REJECTED でもそのまま compile されていた）。
- operation id は tool + args + inputs のハッシュで生成する。provenance と Job の `completed_ops` を compile をまたいで照合できるようにするため（resume の前提）。

## ADR-014 resume は新 Job、冪等キーは上流連鎖、記録は size+mtime で検証する
- 監査で「trim を変更しても loudness の key が変わらず誤スキップする」設計欠陥を予見していたため、key に上流 op の key を含める。
- 完了記録は出力の size / mtime を持ち、一致しない限り再利用しない。`--no-hash` の場合は source を size+mtime で指紋化する。
- resume は元 Job を書き換えず新 Job を作る（履歴と provenance を壊さない）。plan_hash が異なっても key が自己検証するので、一致する操作だけが再利用される。
- 出力の無い operation（check）は常に再実行する。上流が同一引数で再生成された場合、その下流の記録が無傷なら再利用する（key は計画に対して定義され、バイト列に対してではない）。

## ADR-015 revision は再計画、rejected decision は履歴として次版に残す
- `revise` は記録済みの Observation / Timeline から再計画する（メディアは読まない）。却下された (subject, asset) は planner の提案から除外し、却下 decision 自体は status REJECTED のまま次版に残す（理由・actor・時刻は `execution.reviews`）。
- v(n) は `<stem>.v<n>.json` に保存してから置き換える。
- v≥2 は `approved_plan_version == plan.version` になるまで render できない。承認は decision 単位、plan 版の承認は「pending も rejected-cited も無い」ときに自動的に成立する。
- plan_hash は approve/reject で不変、revise で変わる。schema_version はハッシュに含めない。

## ADR-016 Tool は Skill Registry が選び、plan に記録され、compiler は plan からしか読まない
- 事実: PR #4 までは planner と compiler が `ffmpeg-skill/<script>` を直書きし、`SkillSpec.tools` は参照されていなかった（Tool Selector が不在）。
- 決定: `SkillRegistry.select_tool(skill, caps, supports)` を唯一の選択点にする。planner は解決済み skill→tool 表を `plan.steps[].tool` に書く。compiler は step から tool を取り、無ければ `CompileError`。validator は step の skill が実装済みで tool が候補に含まれ adapter が対応することを検査する。
- `ToolRouter` は tool id を対応 adapter へ振り分けるだけで振る舞いを持たない。adapter の登録は `Service.adapter()` の 1 箇所。
- `phase > IMPLEMENTED_PHASE` の Skill は宣言のみで選択不可（`video-agent skills` で NOT_IMPLEMENTED）。存在しない外部 Skill は registry にも adapter にも置かない。
- 追記（PR #5 最終修正）: planner / analyzer / QA に残っていた `DEFAULT_TOOLS` フォールバックを撤去し、`tools` を必須引数にした。Registry を経ずに ffmpeg-skill が選ばれる経路はコード上に存在しない（静的検査 `test_no_tool_id_literals_outside_tool_layer` が `DEFAULT_TOOLS` と tool id リテラルの両方を tool 定義層以外で禁止する）。tool の version も固定名ではなく operation の tool の adapter から引く。

## ADR-017 Ecosystem Contract: Skill package / Tool / Adapter を型で固定し、loader は作らない
- 事実: 実装済みの外部 Skill は `kajisho5/ffmpeg-skill` のみ。将来 Skill（media-analysis / transcription / … / qc）は存在しない。
- 決定: `SkillPackage`（skill_id / name / version / description / capabilities / tools）と `ToolSpec`（tool_id `<skill_id>/<name>` / 実行契約）を `skills/contract.py` に置き、adapter が `package()` で自分の package を宣言、`SkillRegistry` が登録・列挙・検証する。ffmpeg-skill は Reference Skill として `tools/ffmpeg_skill/package.py` で宣言する。
- 既存の `SkillSpec` は production skill（Agent が実現できること）として維持し、改名しない。DECLARED / IMPLEMENTED / AVAILABLE は既存 status に対応付け、新 status は作らない。
- plugin manager / installer / dynamic import / marketplace / remote registry は作らない。package は adapter module と `Service.adapter()` の 1 行で登録される。future skill は production code に登録も stub も置かず、テストは test scope の fake package で契約を証明する。
- planner / compiler / decision / QA に engine 固有ロジックを置かない（静的テスト）。tool id は概念名で、engine は adapter の内側。

## ADR-018 AI Provider は Brain の一部だが execution authority ではない
- 事実: 実装済み Skill package は `kajisho5/ffmpeg-skill`（外部 OSS、100+ stars）のみ。AI provider の本番実装は無く、既存 `AIProvider` は未使用だった。
- 決定: `AIProvider` / `AIRequest` / `AIResponse` / `AIUsage` / `AIProviderError` を契約として固定し、`agent/ai_reasoning.py` だけが provider を呼ぶ。provider は evidence 要約（observation / event の id と計測値）だけを受け取り、structured result を返す。
- AI 出力は untrusted input。intent は registry の実装済み production skill 名に限定し、evidence は既存 observation / event id に限定、tool / argv / command / risk / approval は捨てる。Observation（OBSERVED）は tool 計測のみ（validator が強制）。AI 由来は `AI_GENERATED`。
- 最終 decision authority は system: 計測済み decision と一致する提案は evidence に加わるだけ、それ以外は CONFIRM の review decision で operation を生成しない。BLOCK は AI で覆せない。confidence（AI / 解析の確信）と risk（影響度、registry / policy）は分離。
- budget `analysis.budget.max_ai_calls`（既定 4）、1 call 1 試行、retry 無し、超過は BUDGET 失敗。provider 失敗は AI failure domain（warning + `ai_calls[].error`）で engine incident とは別、plan は決定論的に継続。revision は AI を呼ばない。
- provenance: `provenance.ai_calls[]` / `ai_provider`（provider / model / task / fingerprint / response hash / usage / latency）。credential は request / response / provenance / doctor のどこにも置かない。IR schema は変更しない。
- 作らない: 特定 provider 依存の core、AI による Tool ID 指定・argv・shell・FFmpeg command 生成、AI による IR 直接生成、AI による SkillRegistry / CapabilityResolver / approval の置換。

## ADR-019 Observation is a deterministic evidence layer independent from AI inference
- 事実: Observation は tool 計測からのみ生成されていたが、何を・どの戦略で・どの予算で観測したかは型として存在せず、strategy と budget は記録だけで強制されていなかった。再分析の再利用も無かった。
- 決定: `Asset → AnalysisRequest → Analyzer → Observation → AnalysisResult → Inference → Decision` を固定する。`AnalysisKind` は実装済みの計測（media_probe / silence / loudness）だけを持ち、未実装の名前は登録しない。`Analyzer` は決定論的で、registry が選んだ tool を `ToolAdapter.measure` で呼ぶ以外の実行手段を持たず、AI provider・decision・IR・command に触れない。
- Observation は常に `provenance = OBSERVED`、`source = "<package>/<tool>@<version>"`、`analysis_id` / `analyzer` / `cache_key` を持ち、`validate_observation` を通ったものだけが保存される。AI は Observation を生成も変更もできない（validator と AI evidence 境界で強制）。
- FULL / TARGETED / CACHED_ONLY は実際に動作し、IR には実行した戦略を記録する。TARGETED の kinds は requirements から system が決める。
- `AnalysisBudget` は強制できる項目（calls / seconds）だけを持ち、未対応の予算名は拒否する。AI call budget とは別物。超過は計測を止め、捏造せず、行ごとに記録する。
- `ObservationCache` の key は asset fingerprint + kind + analyzer id@version + tool id@version + params。Observation id、analysis id、cache key、Job の resume 状態はそれぞれ別の identity。
- 明文化: Observation ≠ Inference、Analysis ≠ AI reasoning、AI evidence ≠ executable instruction、Analysis budget ≠ AI call budget、Analysis cache ≠ Job resume state。

## ADR-020 Temporal Events are domain objects distinct from Observations and Decisions
- 事実: Event は analyzer と review が生成する dict 的な record で、type 体系・asset 参照・identity・Session・検証が無く、AI evidence 境界でも区別されていなかった。
- 決定: 時間軸を第一級 domain model として固定する。`TimePoint` / `TimeRange`（秒、検証付き、relation 付き）、`Event`（canonical code + domain type / subtype、asset、range、source、kind + provenance、evidence、generator）、`Session`（project 内の時間的まとまり）。
- Event は Observation（計測）でも Inference（解釈）でも Decision（制作判断）でもない。OBSERVED event は validated tool measurement からの決定論的変換（`events_from_observation`）でしか生まれず、identity は内容 hash。AI 由来は AI_GENERATED / kind INFERRED としてのみ表現でき、OBSERVED に昇格できない（validator と AI evidence 境界で強制）。
- Event type を定義することと検出を実装することを分離する。生成されるのは `IMPLEMENTED_CODES` の 4 code のみ。speech / speaker / slide / camera / scene / caption / incident は schema のみで、fake event で埋めない。
- Session は明示的に構築する domain object（既定は asset 単位）。自動認識・production plan・Project IR の実行内容とは分離し、`plan_hash` にも含めない。
- Observation = measured fact / Event = temporal domain occurrence / Inference = interpretation / Decision = production choice / Session = temporal grouping / Production Plan = production intent / Project IR = execution contract。

## ADR-021 Production Plan is the deterministic bridge between Decisions / Events and Project IR
- 事実: planner は decision から IR 断片を直接組み立て、「何を制作するか」を表す構造（identity / 順序 / 依存 / evidence / 状態）は存在しなかった。
- 決定: `ProductionPlan` / `ProductionStep` を第一級モデルにし、IR の `plan` セクションとして記録する。planner は決定論的（同じ project / decisions / events / constraints → 同じ plan identity）で、tool は SkillRegistry の解決表からしか取らず、実行もしない。
- Event は事実、Decision は判断、ProductionStep は制作工程、IR の video / audio / delivery は実行契約。AI は Inference までで、plan / tool / argv / command / IR / execution に到達できない（validator の domain parameter 限定と leak 検査で強制）。
- plan の status は reviews / approvals から導出する（別の approval 系を作らない）。APPROVED のみ compiler に進み、BLOCK / REJECTED は誰にも覆せない。partial approval は decision 単位のまま。
- Observation ≠ Event ≠ Inference ≠ Decision ≠ ProductionPlan ≠ Project IR ≠ Execution。

## ADR-022 Artifact is a production result with content identity, distinct from File, QA, Delivery and Archive
- 事実: 生成物は path 名の dict として job に記録されるだけで、identity・integrity・provenance 連鎖・delivery / archive の状態が無かった。
- 決定: Artifact の identity は (project, plan, logical name, sha256) の hash。path / job id / timestamp は identity に含めない。同じ plan と同じ bytes は同じ artifact（resume の再利用は job を追記）、revision や内容変更は別 artifact。QA PASS 後の artifact は不変で、promote 前に bytes を再検証する。
- QA（正しいか）と Delivery（納品可能へ昇格したか）と Archive（履歴として保持）を分離。stage は working → candidate → final → archive、delivery_status はその view。final は integrity ok・QA not FAIL・plan APPROVED（現行版）のときだけ。外部 upload は作らず、`channel` を将来の delivery adapter の境界とする。
- 出力 path は compiler が決める。Artifact 層は manifest（`<workspace>/artifacts/registry`）と archive 索引（`<workspace>/archive`）を書くだけで、media を動かさない。naming template は安全な納品ファイル名（metadata）を生成する。
- plan_hash（plan identity）/ ir_hash（execution contract identity）/ artifact sha256（bytes identity）は別物。

## ADR-023 External observation Skills cross a process boundary; their contract is the source of truth
- 事実: media-analysis-skill 0.1.0 が `contract --json` / `run - --json` / `doctor --json` を公開している。transcription-skill には released contract が無い。
- 決定: 外部 Skill は `ToolAdapter` として process boundary（JSON stdin / stdout）だけで接続し、Python import はしない。tools / kinds / capabilities / version / schema は Skill の contract から取り、agent 側で再宣言しない。互換検査（skill id / contract・schema version / execution mode / tool 所有 / provenance）に通らない installation は使わない（silent fallback 無し）。
- Observation の lifting は provenance を簡略化しない（skill / skill_version / tool / external id / fingerprint / parameters / cache）。Skill が所有する cache を agent は二重化せず、状態を記録するだけ。
- 選択は SkillRegistry のまま（ffmpeg-skill を第一候補に維持、media-analysis を第二候補、media-analysis 固有の計測は専用 production skill）。Event は同じ変換で生成し、Event から command は作らない。
- 計測語彙は消費側で正規化する（`loudness_facts` / `probe_facts`）。Observation の data は tool が返した通りに保持し、inference / QA だけが共通 view を読む。QA も同じ adapter boundary（`measurement_args`）で計測する。
- contract が無い Skill は接続しない。stub・推測 contract・fake event は作らない（transcription-skill は 0.2.0 で contract が公開されたため ADR-024 で接続）。

## ADR-024 transcription-skill は「認識まで」を process boundary で接続し、Transcript を Observation、segment を SpeechEvent にする
- 事実: transcription-skill 0.2.0（main）が `skill --json`（id / version / capabilities / tools / engines=EngineSpec / schemas）、`doctor --json`、`run -`（`{"tool","params"}` → `{"ok","tool","result"}`）を公開している。指示書が想定した `contract --json` / `run - --json` は存在せず、実物の transport に合わせた。schema は transcript/0.1・engine-spec/0.1・speech-event/0.1。実装済み engine は faster_whisper（local）のみ。cache hit は保存文書を無変更で返す（asset_id は初回呼び出し側の値）。
- 決定: media-analysis と同じ方式（locate → contract 取得 → 互換検査 → typed request → 1 process → response 検証 → lifting）。Python import・engine 直接実行・model download・ffmpeg 実行は agent 側で一切しない。workspace と allowed_input_roots は adapter が固定し request からは変更不可。engine 選択・model 状態は Skill の contract / selector を尊重し、agent 側に ranking を作らない。`offline` は締める方向にしか作用しない。
- Transcript は認識事実として Observation(kind=transcript, provenance=OBSERVED) に無加工で保存し、provenance（skill / skill_version / tool / transcript id / fingerprint / engine / engine_version / execution_mode / model / model_version / parameters / cache）を保持する。asset identity は fingerprint（Skill の sha256 = agent の asset hash）で照合し、別 asset を作らない。
- SpeechEvent は segment ごとに 1 つ、`speaker_id` は常に null。SpeechEvent ≠ speaker identification。inference / decision / planner / compiler / executor は SpeechEvent を読まない（静的テスト）。Event → command は存在しない。
- transcription 結果は AI inference ではない。AI / LLM / diarization / 字幕 / 編集判断はこの PR に含まれず、SpeechEvent → Inference → Decision は次の段階。

## ADR-025 SpeechEvent は Inference → Decision を経てのみ ProductionPlan に届く（Event → command 無し）
- 事実: PR #13 で SpeechEvent（segment ごと、speaker_id null）が timeline に記録されるが、inference / decision / planner は読んでいなかった。無音は ffmpeg-skill / media-analysis の計測 Event（AUDIO_SILENCE）として同じ timeline にある。閾値は profile に `silence.internal.approval`（generic / conference とも CONFIRM）と `silence.internal.min_seconds`（既定 1.0）があり、発話統合・削除候補の閾値は存在しなかった。
- 決定: `agent/speech_inference.py`（決定的・証拠ベース・AI 無し）が speech_interval / speech_activity / internal_silence_removable / speech_silence_conflict を生成する。閾値は policy キー `speech.merge_gap_seconds`（DEFAULT 0.5）/ `silence.internal.removable_min_seconds`（DEFAULT 2.0）/ 既存 `silence.margin_seconds` を使い、値と provenance を inference data に記録する。
- Decision: 削除候補は `silence.internal.<start>-<end>`（区間付き subject。PlanDiff / revise の suppression が subject@asset キーのため）、approval は policy（CONFIRM）を下限 CONFIRM で適用し AUTO にはしない。conflict と重なる lead / tail trim は CONFIRM に上げる。`speech.continuity` は operation を持たない事実裏付けの decision。
- Plan: 候補は既存 `silence_cleanup` step の removed 区間として keep の補集合になり、step は候補の承認まで PROPOSED（plan REVIEW）。Compiler / Tool 境界は変更なし。
- 実メディア（ja_short ×2 + 3 s 無音）では Whisper の segment が無音側に伸びるため conflict が記録され候補は出ない（安全側）。単語タイムスタンプでの境界精緻化は次 PR 候補。silencedetect end > duration は本 PR で扱わない。

## ADR-026 ProductionContext は Event から決定的に導出する参照中心の中間表現であり、Observation / Event / Decision のいずれでもない
- 事実: Event は単一観測の時間的出来事、Session は人/システムが与えるグルーピングで、「ある時間範囲に複数種別の Event が同時にどう成立しているか」を表す層は無かった。PR #14 の speech inference は SPEECH / AUDIO_SILENCE を直接 timeline から読んでいた。
- 決定: `context/`（model / builder / inference）を追加。ProductionContext = timeline + scope + tracks（type/subtype ごとの event 参照）+ observation / inference / asset 参照、provenance DERIVED、id は内容の hash。境界は Event 自身の start / end のみで、補正・merge・解決はしない。UserDecisionEvent は状況ではない。
- 汎用 inference（source_activity / source_inactivity / transition / conflict）は決定的・ドメイン非依存で、evidence は既存 Event、`data.context_ids` で状況を参照する。conflict は排他ペア表（AUDIO_SILENCE × SPEECH）で記録のみ。AUDIO_SILENCE × AUDIO_ACTIVE は silence tool の keep 区間が margin を含む設計のため排他にしない。loudness のような全体計測は活動を意味しない。
- Decision / Plan は変更しない（汎用 inference は「何が起きているか」まで。「どうするか」は policy / preference / constraint を持つ decision 層）。Context / Inference → step / tool / command の経路は無い（静的テスト）。
- IR: `analysis.contexts`（schema 追加）、validator が参照整合と id 整合を検査、revise は新しい contexts を持ち越す。explain に --context を追加。
- 将来 AI は既存 reasoning boundary 経由で AI_GENERATED inference を生成できるのみ。tool / command / approval / path には届かない。

## ADR-027 Decision は汎用 Decision Engine の不変条件の下でのみ生成し、policy 解決の provenance と basis を Decision 自身に記録する
- 事実: PR #15 までの `decide()` は手続き的で、evidence が空の decision（loudness 計測失敗時の「許容範囲内」）や、approval 値の出所・未知値の扱い・floor が暗黙だった。Decision モデルには type 語彙も basis も無く、`explain --decision` は evidence の一覧止まりだった。既存の precedence（RuleSet、CONSTRAINT は上書き不可）と PR #14 の speech decision の挙動は正しく、壊してはならない。
- 決定: `agent/decision_engine.py`（tool / domain 非依存）を追加し、`decide()` の全 decision をそこから生成する。不変条件: evidence 必須（無ければ生成拒否）、REMOVE / TRANSFORM / DELIVER は計測事実か request の requirement を根拠に持つ（preference / intent / AI 単独は不可、AI 単独は REVIEW のみ）、approval は policy key + 明示 DEFAULT から解決し未知値は CONFIRM、BLOCK* は BLOCK、floor は上げるのみ、BLOCK ⇔ BLOCKED、command / argv / shell / credential 様の内容は拒否（AI 提案 params は削除して記録）。
- 語彙: `type` = KEEP / REMOVE / TRANSFORM / DELIVER / SKIP / REVIEW / BLOCK（既存 decision と 1:1、subject / 文言 / approval / plan への影響は不変）。CONFIRM_REQUIRED 等は approval が既に担うため追加しない。
- basis: settings（key / value / kind / provenance USER・PROFILE・SYSTEM・DEFAULT / rule_id / hard）、approval 解決（key / provenance / notes）、intent（served）、requirements、risk（confidence 非依存）を Decision に記録する。plan_hash には含めない。
- 既存挙動の扱い: USER 明示 requirement による CONFIRM → AUTO の waiver（eval 03）は維持しつつ notes に記録し、CONSTRAINT には適用しない（新規の安全側制限）。loudness 計測が無い場合は decision を出さない（evidence 無し decision の廃止。warning は従来通り）。`silence.internal.approval` の floor CONFIRM は PR #14 のまま。
- validator に `check_decisions` を追加（IR 上で不変条件を再検査。revise で履歴として持ち越された REJECTED decision の evidence は前版のものなので unknown-evidence 検査から除外）。`explain --decision` は basis → evidence chain（inference → context → event → observation → asset / requirement / rule）→ plan step / IR operation まで辿る。
- 対象外: AI / LLM、話者同定、カメラ / スライド選択、新しい decision domain、MCP / plugin / ranking、直接 ffmpeg、Skill 変更、silencedetect end > duration。

## ADR-028 video-editing-skill は CLI contract を境界とする外部編集 Skill として接続し、agent は typed operation だけを渡す
- 事実: kajisho5/video-editing-skill（PR #1、0.1.0、contract video-editing/contract@1）は typed edit request（sources / operations / outputs）を operation graph に検証・コンパイルし、ffmpeg-skill 0.9.x の tool を typed argv で呼ぶ。`video-editing contract --json` / `doctor --json` / `run - --json --workspace D --allowed-input R…`（request は stdin、stdout に 1 文書、error は {ok:false, error:{code, message, retryable, details}}、exit code は error table）。agent 側には既に media-analysis / transcription の外部 Skill adapter パターン（contract が真実、process boundary、PathPolicy、ToolResult 変換）がある。

- 実行: argv list のみ（`run - --json --workspace <op dir> --allowed-input <root>… --ffmpeg-skill-dir <agent が知る ffmpeg-skill>`）、request は stdin、timeout は agent の timeout を options.timeout_seconds として Skill に渡しつつ process boundary（run_process_group、process group kill、exit 124 → CANCELLED/timeout）で強制。`--workspace` は compiler が決めた出力ファイルのディレクトリ（agent workspace 内、executor が作成）、`--allowed-input` は agent PathPolicy の roots + workspace。stdout は厳密に 1 JSON 文書（空 / 非 JSON / 複数文書 / exit≠0 + ok / exit 0 + 出力欠落 / sha256 不一致 / observation 欠落は全て INVALID_RESULT・非 retryable）。
- mapping: execution.outputs[out1]（path / sha256 / size / timeline / observation）→ ToolResult.output・data.artifact・data.timeline・data.observation（OBSERVED、source ffmpeg-skill/probe@ver）、operations[op1] の provenance record → data.operation、commands → ToolResult.commands / provenance（記録のみ。再実行経路は存在しない）。provenance.json の operations[].skill_result に Skill が報告した事実を保存。
- error: Skill の code と retryable を ToolResult.data.error に保持し、adapter が recovery class に写像（INVALID_REQUEST / UNSUPPORTED_* / INVALID_TIME_RANGE / DEPENDENCY_ERROR → INVALID_ARGS(BLOCK)、INVALID_INPUT / PATH_NOT_ALLOWED / MISSING_INPUT → INPUT_MISSING(BLOCK)、TOOL_ERROR retryable → UNKNOWN(1 回再試行)、CANCELLED → TIMEOUT(再試行・timeout 延長)、OUTPUT_ERROR / VALIDATION_ERROR / INTERNAL_ERROR / 非 retryable → SKILL_ERROR(BLOCK、新設)）。recovery.classify_error は Skill が retryable=false と言うものを決して再試行しない。
- lowering: IR video.trim（keep ranges + accurate）→ plan が選んだ tool が video-editing/cut のとき contract の CUT parameters {keep:[{start,end}], precision: frame|keyframe}。ffmpeg-skill/cut への lowering は不変。registry の silence_cleanup 候補は ["ffmpeg-skill/cut", "video-editing/cut"]（宣言順、ranking 無し、fallback 無し。両方利用可能なら従来通り ffmpeg-skill/cut）。video-editing が unsupported とする操作（CROP / FREEZE / REVERSE / IMAGE_INSERT / POSITION）は tool として存在せず、agent が FFmpeg で代替することはない。
- capability: `video-editing` capability は Skill の doctor ok かつ drift 無しのときのみ AVAILABLE（それ以外 MISSING）。registry.select_tool は package capabilities と、resolver が解決する ToolSpec.required_capabilities（encoder:aac / filter:xfade / filter:acrossfade を resolver に追加）を検査し、欠けていれば選択しない。resolver が知らない capability 名は Skill の doctor に委ねる（推測しない）。
- 対象外: 新しい編集機能の追加、video-editing-skill / ffmpeg-skill の変更、Decision Engine への tool 詳細の持ち込み、並列実行、MCP / plugin / ranking。audio-only 入力は video-editing が INVALID_INPUT とするため silence_cleanup の既定候補順は ffmpeg-skill/cut のまま。
- PR #19（同一機能の重複実装）との統合: PR #18 を canonical とし、#19 から (1) operation type ごとの typed lowering module `tools/video_editing/lowering.py`（contract の parameter allowlist と型検証、`supports` = contract 宣言 かつ lowering 実装、contract_only で drift 検出）、(2) 既存 `PathPolicy` object の適用（Service が渡す）、(3) ToolResult.output を agent の path 文字列のまま返し containment は canonical 形で比較（Windows 8.3 名対策）、(4) recovery class INTERRUPTED（CANCELLED の reason が timeout でないもの、BLOCK）、(5) Skill の OBSERVED probe を agent Observation model に lift する `lift_observation` と provenance.json `skill_observations`、(6) capability evidence の operations / contract_only / unsupported を取り込んだ。#19 の「package capability UNKNOWN を許容」する select_tool と semantic_deletion への候補追加は採用しない（UNKNOWN は AVAILABLE ではない / 未実装 skill に候補を足さない）。


## ADR-029 video-editing-skill の編集操作（concat / speed / resize / fit / fill / overlay）は明示 requirement → Decision → Plan → IR operation として計画し、Planner から Skill への近道は作らない
- 事実: PR #18 の adapter は contract の全 tool（TRIM / CUT / CONCAT / SPEED / FIT / FILL / RESIZE / OVERLAY）を request 化できるが、planner が出す IR operation は video.trim だけだった。「Skill が対応している」と「agent が計画・実行・検証できる」は別の段階である。
- 決定: 6 operation を `agent/editing.py` の語彙として追加する。段階は Requirement（`edit.concat` / `edit.speed` / `edit.resize` / `edit.fit` / `edit.fill` / `edit.overlay` と `edit.<op>.<param>`、明示の `--set` のみ。キーワード抽出・推論・DEFAULT による起動は無い）→ Decision（type TRANSFORM、evidence は requirement id + probe observation、approval は policy key `video.<op>.approval`（既定 CONFIRM、明示 USER 要求は PR #16 の規則で waiver、CONSTRAINT / BLOCK は不変））→ ProductionPlan step（skill `video_concat` / `video_speed` / `video_resize` / `video_fit` / `video_fill` / `video_overlay`、tool は registry が選ぶ `video-editing/<op>` のみ）→ IR `video.operations[]`（type / asset(subject) / input / inputs / output / image / allowlist parameter / temporal_scope / decision_ids、concat は segments[{input, track, source_range, timeline_range}] と timeline_duration）→ compiler `lower_video_edit`（allowlist の key を名前で写すだけ。tool が operation の tool でなければ CompileError、代替 engine 無し）→ VideoEditingAdapter（PR #18 の lowering / 境界のまま）。
- 順序は固定（trim → concat → speed → resize → fit | fill → overlay → loudness → export → check）。concat があれば trimmed 入力を宣言順に結合した論理出力 `programme` が subject になり、以降の操作・loudness・delivery は programme に適用される（入力ごとの loudness は結合で無効になるため 1 回だけ。evidence は各入力の測定）。concat が無ければ各 asset が subject（既存挙動と byte 単位で同じ plan）。
- 安全側: 1 入力での concat / video stream の無い入力 / fit と fill の同時要求 / capability 欠落 / doctor 失敗 / drift → BLOCK decision（`plan_status` は step の有無に関わらず BLOCK decision があれば BLOCKED）。値域外（speed 0.25–4 かつ ≠1、width 偶数 16–8192、aspect W:H、overlay 画像は存在する PNG / JPEG で traversal 無し、opacity 0–1 など）は plan 時に EditRequirementError（ValueError）で拒否し、補正・推測しない。validator は IR 側で同じ規則（語彙外 key、順序、programme の存在、二重 concat、fit+fill、画像の allowed_inputs 内、step の存在）を検査し、schema は video_op を additionalProperties=false にする。
- QA / Artifact: 期待 duration は IR から導く（kept ranges → concat timeline（transition 分の overlap を引く）→ speed factor）。`delivery_subjects` が asset か programme を返し、QA と artifact 登録は subject 単位（artifact.source は結合した全 asset）。
- 対象外: LLM / 自律編集、話者・シーン・カメラ・スライドの推論、字幕、色、音声マスタリング、サムネイル、モーショングラフィックス、cloud / MCP / plugin。conference 固有ロジックは入れない（generic）。video-editing-skill / ffmpeg-skill は変更しない。

## ADR-032 qc-skill は最終 promotion の gate として接続し、report は agent 自身が算出した sha256 と一致する admission を通ったものだけを QA item にする（agent の QA は削らない）

## ADR-033 `audio.production=true` は audio path を有効化するだけで、`audio.extract` の CONFIRM は専用の明示 requirement `audio.extract=true` でしか waive しない（P1-1、2026-09-05）
- 事実: PR #21 の `decide()` は `audio.extract` decision の approval を `approval_for("audio.extract", explicit=<audio.production requirement>)` で解決していた。engine の規則「USER がその操作を明示的に求めた requirement は CONFIRM を waive する」に generic な switch を渡していたため、`--set audio.production=true` だけで video container の音声抽出（映像を納品しない semantics 変更）が AUTO になり、確認なしに実行できた。他の audio 操作（`audio.gain` 等）はすべて自分のキーの requirement を渡しており、`audio.extract` だけが不整合だった（PR #21 監査 P1）。
- 決定: 語彙に `audio.extract`（bool、明示のみ、`audio.production` 無しは他の `audio.<op>` と同じく ambiguous として拒否）を追加し、`audio.extract` decision の `explicit` には `audio.extract=true` の requirement だけを渡す。switch は `explicit` に渡さない。engine の waiver 規則（USER のみ、CONSTRAINT には不適用、BLOCK は不変、floor は上げるのみ）・AUTO / CONFIRM / BLOCK の意味・Approval / review の仕組みは変更しない。既存の承認経路（`approve --decision <id>` / `render --approve`）はそのまま使える。request-scope の policy 値 `--set audio.extract.approval=AUTO|BLOCK` は ADR-027 どおり効く（decision key を名指しする明示情報。profile の CONSTRAINT には負ける）。
- 決定（planner）: video container の audio path の operation・step・delivery target は、その asset の `audio.extract` decision id を `decision_ids` に含める。pending の CONFIRM は step を PROPOSED に留め（partial approval でも走らない）、REJECTED は rejected-cited として render を BLOCK し validator も拒否する。revise で extract proposal が落ちた asset は audio path に何も計画しない（summary に記録。audio concat の入力なら concat も計画しない）。映像を静かに落とす経路は残さない。
- 決定（validator）: `check_decisions` に「`approval` は basis の `resolved` より緩くできない（CONFIRM→AUTO の書き換えは拒否、BLOCK への引き上げは可）」「status APPROVED の CONFIRM decision には APPROVED の review record が必要」を追加（generic、audio 固有ではない）。
- 保証: `audio.production=true` だけでは `audio.extract` は CONFIRM のまま → plan REVIEW → render は WAITING_FOR_APPROVAL、Skill process は起動しない。resume は同じ gate を通る（job の再利用は approval ではない）。compiler は render gate の後でしか呼ばれず、operation には decision id だけが渡る。
- 対象外: speaker → camera switching（GAP §22）、HDR / lower_third / image_overlay、他の approval key の見直し。既知（pre-existing、main でも再現）: approve 後に revise すると v1 の USER_DECISION event が v(n) に無い decision id を cite し validator が error を出す（P2、別 PR）。

## ADR-034 Revision の review 履歴は `revision.history[].reviews` に版ごと保持し、持ち越した USER_DECISION event はそこに対して解決する（active decision には昇格しない）（P2-A / P2-B、2026-09-05）
- 事実: `revise` は USER_DECISION event を全件 v(n+1) へ持ち越すが、v(n+1) の decision 集合は「REJECTED の v(n) decision + 再計画した decision」だけで、`execution.reviews` も REJECTED 分しか残らなかった。APPROVED だった v(n) decision を cite する承認 event は v(n+1) に解決先が無く、validator が `evidence not found` を出して v(n+1) は validate / render できなかった（approve → 追加要件で revise、という通常操作で発生。main で再現）。
- 決定: version 境界の意味論を次のように固定する。(1) v(n+1) の active decision は再計画の結果と REJECTED の履歴だけ。v(n) の承認は v(n+1) の承認ではない（`approved_plan_version=None`、`execution.reviews` は REJECTED 分のみ、`approvals` は空）。(2) v(n) の review record は `revision.history[].reviews` に verbatim で保存する（改ざんしない・落とさない。schema は additive のため 1.2 のまま、migration 無し）。(3) 持ち越した USER_DECISION event は「その版のレビュー」であり、validator は `metadata.plan_version < plan.version` の event に限り、evidence を active decision または `revision.history[].reviews` / `rejected_decision_ids` に対して解決する。history に無い id、または現在版を名乗りながら historical id を cite する event は従来どおり error。operation / step が historical id を cite することは変わらず不可。(4) resume は版を跨いでも approval gate を先に通り、job は新規（`resumed_from` を記録、変更された operation は再実行）。
- 決定（P2-B）: `audio.concat` の approval は自身の明示 requirement `audio.concat=true` を `explicit` にする（ADR-033 と同じ規則。switch `audio.production` は path の有効化のみ）。挙動は不変（AUTO のまま）、basis の notes / evidence が正しいキーを指す。
- 対象外: speaker / camera / multicam / sync、TimelineMap、schema 1.3、AI provider、新 Skill。

## ADR-044 複数ソースの同期は ffmpeg-skill/sync の測定を `sync` Observation（OBSERVED）として保持し、既存 TimelineMap の offset / drift_ratio に接続する（判断は生成しない）（2026-09-05、PR #25。番号は main 側で ADR-036〜043 が並行して採番されたため、それらの後（044）に繰り下げ）
- 事実: TimelineMap（offset_seconds / drift_ratio / to_master）と IR `timeline.timelines` は PR #9 から存在するが、offset を書く経路が無く常に 0.0 / 1.0 だった（GAP §16、MASTER_SPEC「not available yet」）。ffmpeg-skill 0.9.1 は `sync.py`（音声 cross-correlation、`--json` で offset_seconds / confidence / drift{drift_ppm, confidence, …}、失敗は exit 1 + `{"status":"failed","error":{kind,message}}`）を提供し、agent の catalog（`ffmpeg-skill/sync`）にも登録済みだったが、registry では phase 2 の `multi_source_sync` に宣言されているだけで planner / analyzer は使っていなかった。
- 決定: analysis kind `sync`（measurement skill `sync_analysis` → tool `ffmpeg-skill/sync`、capability ffmpeg / ffprobe / ffmpeg-skill）を追加する。pairwise: 入力の先頭を reference（master clock）とし、audio を持つ他の各入力を target として測る。既存 `_observe`（cache → budget → tool → validation）を通り、cache key は両 asset の fingerprint。Observation は kind `sync`、asset_id = target、data = {offset_seconds, confidence, meaning, drift?, reference_asset_id, target_asset_id, min_confidence, applied_to_timeline}、parameters = tool に渡した {max_offset, analyze_seconds, fix_drift} のみ、provenance OBSERVED。paths / commands は data に入れない。`replace_audio` / `trim_second` / `output` は測定では決して渡さない（同期出力の生成は agent の責務ではない）。
- 符号と単位は tool のまま: `offset_seconds > 0` = target（tool の `second`）が reference より遅く始まる。drift は tool の `drift_ppm` を保持し、TimelineMap の `drift_ratio = 1 + drift_ppm / 1e6`（同じ量の単位換算、tool の「ratio > 1 = target が長い / 遅い」と TimelineMap の `to_master(t) = t / drift_ratio + offset` に一致）。agent は相関計算を一切持たない。

- 境界: sync は Event にしない（`events_from_observation` に分岐なし）。inference / decision / planner は読まない（plan_hash は sync 有無で同一、テストで保証）。3 本以上は reference に対する pairwise observation の集合で表す（global solver は作らない）。schema は 1.2 のまま（observation / timelines とも既存構造）。
- 対象外: speaker / camera / multicam 切替、SyncEvent、offset 補正の Decision、同期出力の生成、multicam.py の利用、AI。

## ADR-037 `SkillRegistry.select_tool()` の Provider 衝突は3段階ポリシー（明示 → 既定 → 拒否）で解決し、宣言順の暗黙 first-match-wins は廃止する（Phase 3、AI-video-production-OS ROADMAP.md、2026-09-06）
- 事実: `media_probe` / `silence_analysis` / `loudness_analysis`（ffmpeg-skill vs media-analysis）と `silence_cleanup`（ffmpeg-skill vs video-editing）の4 production skill は、両方の package が実際に installed されている環境では2件の実行可能な tool 候補を持つ。従来の `select_tool` は `spec.tools` の宣言順で最初に `supports()` が true を返す候補を無条件に選んでおり、利用者がどちらを使うか指定する手段が無かった（AI-video-production-OS の CAPABILITY_MODEL.md が Phase 3 の既知課題として明示: 「`SkillRegistry.select_tool()` currently picks the first candidate in a hardcoded ordered list — a silent default this OS replaces」）。
- 決定: `select_tool(name, caps, supports, explicit=None, default=None)` に2引数を追加する。実行可能な候補が0件または1件なら従来どおり（このパスは変更なし、既存の全 production skill の大半はここで完結する）。2件以上（実際の Provider 衝突）のときだけ、(1) `explicit`（呼び出し側が渡す package 名、`skills/providers.py` の `explicit_providers()` が `provider.<skill>=<package>` requirement から抽出。候補に無ければ None を返し利用可能な provider 一覧を理由に含める — 静かに無視しない）→ (2) `default`（同じく `providers.py` の `default_providers(workspace)`。OS 既定の `DEFAULT_PROVIDERS`（この4 skill はいずれも `ffmpeg-skill` — 従来の実効挙動と同一）を `<workspace>/providers.json` の `{"skill_name": "package"}` で上書きできる）→ (3) どちらも解決しなければ拒否（tool=None、理由に候補・件数・`--set provider.<skill>=<package>` と `providers.json` の両方の設定方法を含める）の順で解決する。`resolve_tools()` / `availability()` は per-skill の `explicit` / `default` 辞書を受け取り、同じ規則を一括適用する。`agent/decision.py` の `decide()` も同じ2辞書を受け取り、`cap_block()` の BLOCK 判定を `Service.tools_for()` が作る tools 表と常に一致させる（食い違い防止）。
- 決定（Service）: `Service._providers(user_requirements)` が `(explicit, default)` を1箇所で組み立て、`tools_for()` / `require_tools()` / `_reason()`（→ `decide()`）/ `skills()` が同じ組み立てを使う。`plan()` / `revise()` は `provider.<skill>` の skill 名を registry の実在 skill 名と照合し、存在しない名前は即座に ValueError（何にも効かない設定を黙って受理しない）。`REQUIREMENT_PREFIXES` に `provider.` を追加（他の requirement と同じ `--set` / provenance 記録の対象になる）。
- 保証: `DEFAULT_PROVIDERS` は4つの既知衝突すべてに `ffmpeg-skill` を設定しており、`explicit` も `providers.json` も無い環境（今日の全デプロイ・テスト環境）は Tier 2 のこの既定で従来と同一の tool を選ぶ（`video-agent skills` の出力・real-Skill integration テストの選択結果は不変）。一方、テスト用に登録順を意図的に入れ替えて別 package を選ばせていた既存テスト（`SkillToolBoundaryTests` / `EcosystemContractTests` / `VideoEditingAdapterTests` の3件）は、宣言順ではなく明示の `provider.<skill>=<package>` requirement で選ぶよう更新した — 「先頭に書けば勝つ」という暗黙の仕組みへの依存を、意図が読める明示の選択に置き換えるのが本 ADR の趣旨そのものであるため。
- 対象外: OS レベルの Capability id 名前空間（`measure.audio.loudness` 等）の導入 — この agent 自身の `SkillRegistry` は production skill 名（`loudness_analysis` 等）の粒度で衝突を解決しており、`provider.<skill>=<package>` の `<skill>` もこの名前を指す。ProductionPlan の Operation に provider を記録する形式（CAPABILITY_MODEL.md Tier 1 の元々の想定）、Capability レジストリの独立した永続ストア、複数 workspace 間で共有する集中設定サービス。

## ADR-038 `Artifact` に `produced_by`(`capability_id`/`provider_id`)と `derived_from` を追加し、`Service.adapter()` を capability 駆動の1ループへ統一する（Phase 4、AI-video-production-OS ROADMAP.md、2026-09-06）
- 事実（既存との重複確認）: `ARTIFACT_MODEL.md` §4 は `produced_by: {capability_id, provider_id, skill_id, skill_version, operation_id}` を求めるが、実装前に照合したところ `skill_version` は既存の `Artifact.tool_version` と、`operation_id` は既存の `Artifact.operations`（複数の producing operation id）とそれぞれ同じ情報であり、重複するフィールド名を新設しない。真に不足していたのは `capability_id`（どの production skill が作ったか）と `provider_id`（実際に実行した package — ADR-037 の Tier 1/2/3 が初めて明示的な選択にした情報）の2つだけだった。`derived_from`（§3）は `ARTIFACT_MODEL.md` 自身が「FUTURE、PROPOSED、まだどこにも実装されていない」「既存の Plan/Operation モデルが持つ情報の projection であり新しい真実の源ではない」と明言しており、traversal API や graph query の類は明示的に対象外とされている。
- 決定（Artifact）: `capability_id: str = ""`（= producing Operation の `skill`、例 `"delivery_export"`）、`provider_id: str = ""`（= `tool.split("/", 1)[0]`、例 `"ffmpeg-skill"`）、`derived_from: List[str] = []`（`source` のうち `ArtifactStore.get()` で実在が確認できるもの — 生の source asset id は除外し、実際に他の登録済み Artifact である場合だけを graph edge として記録する）を追加。すべて additive・既定値ありで、`Model.to_dict/from_dict` は dataclass のフィールドを反射的に扱うため、既存のディスク上の Artifact JSON はスキーマ変更・migration 無しでそのまま読める（ADR-034/036 と同じ「additive only」判断）。`Service._register_artifacts()` の唯一の `Artifact(...)` 構築箇所で、既に手元にある producing Operation（`exp`）と `ArtifactStore`（`st`）から機械的に埋める。
- 決定（Service.adapter()）: ffmpeg-skill（Reference Skill、この codebase に無条件で実装されており、構築失敗が唯一 catch されない特別なケース）はそのまま先頭に残し、残り9 Skill package（media-analysis / transcription / video-editing / audio-production / subtitle / thumbnail / color-grading / motion-graphics / qc）の個別 `if` 分岐（4件）と既存の一部ループ（5件）を1つのタプルのリスト × 1ループへ統合した。各 Skill の実際のコンストラクタ引数の違い（`allowed_inputs` の既定値が `[]` になるか `[workspace]` になるか、`ffmpeg_skill_dir` を取るか等）は一切変更せず、行ごとに保存 — 「新しい Skill を1つ増やす」操作が「新しい `if` 分岐を書く」から「表に1行足す」になる、という roadmap の要求を字義通り満たす一方、コンストラクタ引数の差異を偽の統一インターフェースで覆い隠すことはしない（そうした汎用アダプタ・インターフェースの設計自体は、実際に必要になった時に検討する未解決の設計課題として `ARTIFACT_MODEL.md`/`ROADMAP.md` の議論に残す）。
- 保証: 上記はすべて「機械的・挙動保存」のリファクタであり、新しい動的ロード・plugin・第三者 Skill 発見の仕組みは一切導入していない（それは roadmap が明示的に Phase 7 に先送りしている領域）。`tests/test_unit.py`: 198 passed（既知の環境依存失敗4件のみ、Phase 3 の時点と同一）。`tests/test_integration.py`（実 ffmpeg + 実9 Skill、モック無し）: 全件通過を確認（実行ログは PR 本文参照）。
- 対象外: `derived_from` を辿る graph query / traversal API、reachability によるガベージコレクション、OS レベルの Capability id 語彙をこの agent 自身の production skill 名の外に新設すること、Skill ごとに異なるコンストラクタ引数を汎用化する第三者ロード可能なアダプタ・インターフェース（Phase 7 の対象）、`ArtifactModel.md` §5/§6（lifecycle stage・キャッシュ）— これらは既存実装のままで変更が要求されておらず、本 ADR の対象外。

## ADR-039 `QAItem` に `threshold_source`（`plan` / `rule`）と `subject_artifact_id` を追加し、既に実装済みの plan-conformance 検査を可視化する（Phase 5、AI-video-production-OS ROADMAP.md、2026-09-06）
- 事実（実装前の照合で判明した既存実装）: `QC_ARCHITECTURE.md` §5 は「duration が Plan の trim/concat ステップの意図と一致するか、という plan-conformance check は audited ecosystem のどこにも存在しない real gap」と述べているが、`qa/checks.py` の `run_qa()` を実装前に直接読んだところ、`kept = subject["duration"]`（kept ranges → concat timeline → speed factor、IR から計算、測定値ではない）と実測 duration を `dur_tol` で比較する PASS/FAIL 判定、および `target_lufs`（IR の loudness normalization 決定由来）と実測 LUFS を比較する判定は、このセッション以前から `run_qa()` に実装済みだった。つまり Phase 5 が求める「検査そのもの」の大部分は既に存在しており、`QC_ARCHITECTURE.md` §5.1/§5.2 が名指しする本当に欠けている部分は (a) 個々の `QCFinding`/`QAItem` がどの Artifact を検証したかを辿れる `subject_artifact_id` フィールド、(b) その閾値が Plan 由来（"plan"）か固定ルール由来（"rule"）かを finding 自体に記録する provenance の可視化、の2点だけだった。
- 決定: `QAItem` に `threshold_source: str = "rule"`（既定）と `subject_artifact_id: str = ""` を追加。`run_qa()` の対象ごとのループ冒頭で `artifacts.artifact_id(project_id, plan_id, art, sha256(path))` を計算し（`_register_artifacts()` が後で計算するのと同じ関数・同じ入力 — Artifact 登録前でも同じ id を先取りできる）、そのイテレーションで追加された全 `QAItem` に一括で書き戻す（`start_idx` から現在までのスライス）。ファイルが読めない場合（probe 自体が失敗する経路）は `subject_artifact_id=""` のまま probe FAIL item だけを個別に記録し、QA 全体をクラッシュさせない（`OSError` を握りつぶす — これは trace 用の付随情報であり、QA の判定そのものより優先度は低い）。`threshold_source="plan"` は実際に IR 由来の値と比較している2箇所（video/audio の `duration` 判定、`audio/loudness` 判定）にだけ明示し、それ以外（video_stream の有無、HDR/CFR/FPS の一致、delivery の platform check、true peak 等の固定しきい値）は既定の `"rule"` のまま変更しない。
- 対象外: `qc-skill`（外部 Skill）自身の `QCReport` JSON 契約への `subject_artifact_id` 追加 — その内部の36 checks がどれだけ plan 由来でどれだけ固定ルールかをこの agent は個別に知る手段がなく、`qc_items()` が包む `QAItem("qc", ...)` は正直に既定の `"rule"` のままにする（qc-skill に渡す `rules_for_subject()` の値の一部が実際は plan 由来であっても、それを可視化するには qc-skill 側の contract 変更が要り、それは別リポジトリの変更であって本 PR の対象外）。CONCAT/TRIM 以外の operation 種別ごとの新しい plan-conformance 次元（色補正・オーバーレイの座標一致など）の追加、`ExecutionResult` の成功報告と QC 結果の乖離を独立した fact として記録する仕組み（§5.3、今回は追加しない）。
- 保証: 全て additive（`QAItem` の2フィールドは既定値あり）、既存の判定ロジック・PASS/FAIL/WARN/UNKNOWN の意味論・worst-wins 集約は一切変更していない。`tests/test_unit.py`: 198 passed（既知の環境依存失敗4件のみ）。`tests/test_integration.py`（実 ffmpeg + 実9 Skill、モック無し）: 全件通過を確認（実行ログは PR 本文参照）。実際の render で `dur["threshold_source"] == "plan"` かつ `dur["subject_artifact_id"] == art["id"]`（登録済み Artifact の実 id と一致）であることをテストで確認。

## ADR-040 `ProductionReceipt`（Artifact type `PRODUCTION_RECEIPT`）を実行完了ごとに1件発行する（Phase 6、AI-video-production-OS ROADMAP.md、2026-09-06）
- 事実: `SPEC.md` §6 / `PROVENANCE.md` §4 が定義する `ProductionReceipt`（`{id, project_id, plan_id, plan_hash, ir_hash, input_artifact_ids, output_artifact_ids, skill_versions, tool_versions, decisions, qc_report_ids, warnings, failures, created_at}`）は「既存の部品の合成であり新しい概念ではない」と明言されている。実装前に `Service.render()` を直接読んで確認したところ、`skill_versions`/`tool_versions`/`plan_hash`/`ir_hash` は `ir.doc["provenance"]` / `ir.doc["source"]` に既存、producing Operation → Artifact の関係は `_register_artifacts()`（ADR-038 の `capability_id`/`provider_id`/`derived_from` を含む）に既存、decision の全体は `ir.doc["decisions"]` に既存。真に新設が必要だったのは、これらを1つの JSON にまとめて実際に Artifact として登録する処理だけだった。
- 決定（I5 の解決、`OPEN_ARCHITECTURAL_QUESTIONS.md` が「Phase 6 で解決必須」と明示していた問い）: receipt は `Executor.run()` が何らかの終端状態（`COMPLETED` / `FAILED` / `BLOCKED` / `CANCELLED`）に達した時点で必ず1件発行する — `PROVENANCE.md` §4 の「'completed' とは Plan が実行を終えたことであり、全項目に合格したことではない」という定義どおり、QA/QC が FAIL でも receipt は発行し `failures` に記録する。逆に、実行そのものに到達しなかった経路（`REJECTED`/`BLOCKED` な decision で `render()` が approval gate より前に return する、`WAITING_FOR_APPROVAL`、`validate()` 失敗）では一切発行しない — 何も実行されていない以上、記録すべき実行の事実が無い。`_register_artifacts()` 自身が `ArtifactError` で早期 return する経路（Artifact 登録そのものが失敗する、稀な内部エラー）は本 PR では対象外のまま残す（既存の `report.json`/`report.md` 生成と同じく、その手前で return するため）。
- 決定（I7 の解決、`PROVENANCE.md` 自身が "non-blocking" と明言）: `warnings`/`failures` は仕様どおり自由記述文字列のリストにする（`QCFinding` id を参照する構造化案は採らない — ドキュメント自身がその設計を「今すぐ答える必要のない改善候補」と位置づけている）。中身は `qa.items` の WARN/FAIL 行 + 実行自体が非COMPLETEDならその旨 + `ir.doc["analysis"]["warnings"]`。
- 決定（実装）: 新規 `audit/receipt.py` の `build_receipt()` が body を組み立て、`id`（body 自身のフィールドから計算する自己記述的な content hash、`"receipt_" + stable_hash(...)`）と `created_at` を最後に付与する。`Service.render()` は `write_audit(provenance.json)` の直後に `receipt.json` を書き出し、他の Artifact と全く同じ経路（`ArtifactStore.integrity()` → `artifact_id()` → `ArtifactStore.register()`）で `type="PRODUCTION_RECEIPT"` の Artifact として登録する（新しいサブシステムではなく、既存の Artifact 基盤に型を1つ追加しただけ）。`ARTIFACT_TYPES` に `PRODUCTION_RECEIPT` を追加（この enum はコード上どこにも強制検証されておらず、ドキュメント用の tuple であることを確認済み）。receipt 自身の `Artifact.id`（ファイル内容の sha256 由来、他の Artifact と同じ規則）と receipt body 自身が持つ `id`（body フィールドの content hash、SPEC.md の定義どおり）は意図的に異なる2つのハッシュとして併存させる — 前者は ArtifactStore の登録・検索キー、後者は receipt という文書そのものの自己同一性で、両方とも "content hash" だが答える問いが違う。
- 対象外: `qc_report_ids` の実装 — この codebase では qc-skill のレポート自体が独立した Artifact として登録されておらず（`qc_items()` はインラインで admit するだけ）、存在しない Artifact id を捏造するよりは空配列のままにする方が正直（PASS/WARN/FAIL の実質情報はすでに `warnings`/`failures` に入っている）。`_register_artifacts()` が `ArtifactError` で早期 return する経路への receipt 発行、再実行・resume 時の receipt の重複排除ポリシー（今回は「render 呼び出しごとに新しい receipt」という最も単純な規則を採用し、resume で一部 op が再利用されても新しい receipt を作る）。
- 保証: 既存の `report.json`/`report.md`/`provenance.json` の生成・内容は変更していない（receipt はその後に追加で書き出すだけ）。`ARTIFACT_TYPES` の追加は additive。`tests/test_unit.py`: 199 passed（既知の環境依存失敗4件のみ）。`tests/test_integration.py`（実 ffmpeg + 実9 Skill、モック無し）: 全件通過を確認（実行ログは PR 本文参照）。新規テストで、COMPLETED の render では receipt の全フィールドが実データと一致すること、FAILED の render でも receipt が発行され `failures` に実行失敗の事実が入ること、receipt が `svc.artifact()` で他の Artifact と同じ経路で読めることを確認。

## ADR-041 実データでの検証中に発見した2件のライブ・バグを修正する: 死んでいた ffmpeg-skill バージョンゲートの配線、および6箇所の Skill 探索が明示的な「不在」指定を無視して兄弟ディレクトリへフォールバックしていた問題（AI-video-production-OS ROADMAP.md 完了後の実データ検証、2026-09-06、PR #46）

- 事実1（死んだバージョンゲート）: `grep -rn "version_supported" src/` の結果、`FfmpegSkill.version_supported()` を呼んでいるのは `tests/test_unit.py` と `tests/test_integration.py` の中だけで、`capabilities/resolver.py` の `caps["ffmpeg-skill"] = Capability("ffmpeg-skill", "AVAILABLE", ...)` は `locate_ffmpeg_skill()` がチェックアウトを見つけさえすれば無条件で `AVAILABLE` にしており、`version_supported()` を一度も参照していなかった。つまり「0.9.x は検証済み、0.10 は未検証」というコメント・ADR上の主張は、実行時には一切強制されていない宣言だけの安全策だった。さらに `tools/ffmpeg_skill/package.py` の `SUPPORTED_RANGE = "0.8.4 <= v < 0.9"` という表示用文字列は、`locate.py` の実際の範囲（`< 0.10`）ともすでに食い違っており、三重に不整合な状態だった。
- 事実2（Skill 探索の明示的オーバーライド無視）: 上記の調査の副産物として `tests/test_unit.py` の4件が、この session とは無関係に安定して失敗することを確認した（`git stash` で本 PR の変更前の `main` に戻しても同一の失敗を再現）。原因は `locate_transcription`/`locate_media_analysis`/`locate_video_editing`/`locate_audio_production`/`locate_ffmpeg_skill`、および `subtitle`/`thumbnail`/`color-grading`/`motion-graphics`/`qc` が共有する `skill_process.locate_cli_skill` の計6箇所すべてが同じ形の候補リストを組んでいたこと: `explicit` 引数や `*_DIR` 環境変数を「まず試す最優先候補」として先頭に追加するだけで、それが見つからなくても `~/.claude/skills/<name>`・`./vendor/<name>`・`../<name>` という「推測」候補への fallthrough を止めていなかった。このリポジトリ自身の実運用レイアウト（`video-production-agent` の兄弟ディレクトリとして全 Skill リポジトリが `/home/user/` 直下に並ぶ、まさにこのエコシステムが意図する構成）では、`explicit="/nonexistent"`（＝「ここには無い」という明示的な指定）を渡しても `../<skill-name>` が実在の別チェックアウトに解決してしまい、`MISSING` を期待するテストが `AVAILABLE` を返して失敗していた。この4件は Phase 4/5/6（PR #43/#44/#45）のログに「4 known environmental failures, unrelated」として複数回記録されていたが、これまで実際には調査されていなかった。加えて `media_analysis/locate.py` の最終フォールバック `shutil.which("media-analysis")` は `path=env.get("PATH")` を渡し忘れており、テストが `PATH` を偽装しても実機の `PATH` 上の実インストールを拾ってしまう、同種の独立したバグも同時に見つかった。
- 決定1: `capabilities/resolver.py` の ffmpeg-skill 解決を `skill.version_supported()` を実際に参照するよう変更。範囲内なら `AVAILABLE`、範囲外なら `DEGRADED`（`MISSING` ではない — ffmpeg-skill の構築自体は ARCHITECTURE_REVIEW §1.7 通り無条件のままで、実行を止めない。既存の `SkillRegistry` は `DEGRADED` を `AVAILABLE` と同様「使用可能」として扱う既存の意味論と整合する）。`evidence` に `version_supported: bool` を追加。`package.py` の `SUPPORTED_RANGE` は手書き文字列をやめ、`locate.py` の `SUPPORTED_MIN`/`SUPPORTED_MAX_EXCLUSIVE` から動的に生成するよう変更（今後この2箇所が再びずれることを構造的に防ぐ）。
- 決定2: `explicit` 引数または `*_DIR` 環境変数のどちらかが与えられている場合、それらを「権威的（authoritative）」候補として扱い、そこにチェックアウトが無ければ即座に見つからない扱いとする——`~/.claude/skills/*`・`./vendor/*`・`../*` という「推測」候補へは一切フォールスルーしない。両方とも未指定のときだけ、従来どおり推測候補を試す。対象は `ffmpeg_skill`/`media_analysis`/`transcription`/`video_editing`/`audio_production`/`skill_process.locate_cli_skill`（`subtitle`/`thumbnail`/`color_grading`/`motion_graphics`/`qc` が共有）の6箇所全て。コンソールスクリプト（PATH）へのフォールバックは変更していない — これは「別の推測」ではなく「別のインストール形態」であり、明示的な override が失敗した後もなお正当な最終手段のため。`media_analysis/locate.py` の `shutil.which("media-analysis")` には欠けていた `path=env.get("PATH")` を追加。
- 検証（決定1、"verify then pin" の既存規律どおり）: `tests/test_integration.py`（実 ffmpeg + 実9 Skill、モック無し、48件）を ffmpeg-skill 0.10.0 に対して実行し、`SUPPORTED_MAX_EXCLUSIVE` を上げる前は `FfmpegSkillContractTests::test_version_and_scripts` の1件と、observation の `source` 文字列を `"ffmpeg-skill/probe@0.9"` に決め打ちしていた3箇所（`VideoEditingRealTests`/`VideoEditingOperationsRealTests`/`AudioProductionRealTests`、実際は7 FAILED — 後者3ファイルは複数テストが同じヘルパーの1箇所を共有）以外はすべて通過することを確認した——すなわち 0.10.0 でも実際の変換結果・パス・アーティファクトは1件も壊れておらず、失敗はすべて「0.9 決め打ち」という表明のズレだけだった。これを根拠に `SUPPORTED_MAX_EXCLUSIVE` を `(0, 11, 0)` へ更新し、上記3箇所の decided-string assertion を `locate_ffmpeg_skill().version` を参照する動的な比較に修正（将来また上がっても壊れない）。更新後、`tests/test_integration.py` 48件全て通過を確認。
- 対象外: 6箇所の locate 関数の統合（重複コードの共通化）——今回は挙動のバグ修正のみに留め、リファクタリングは別スコープとする。`*_DIR` 環境変数と `explicit` 引数のどちらを優先するかの意味論変更は無し（従来通り `explicit` が先）。コンソールスクリプト（PATH）検出自体の追加テストカバレッジ拡充。
- 保証: 全て additive/修正のみ、既存の探索順序（何も指定しない通常運用時）は完全に不変——`explicit`/`*_DIR` を渡さない全既存呼び出し（本番コード・既存テスト含む）は一切影響を受けない。`tests/test_unit.py`: 210 passed（新規回帰テスト7件 `LocateAuthoritativeOverrideTests` を含み、以前「既知の環境依存失敗」として繰り返し記録されていた4件はすべて解消——実際は環境依存ではなく再現可能なコードのバグだった）。`tests/test_integration.py`（実 ffmpeg + 実9 Skill、モック無し）: 48 passed, 0 failed。

## ADR-042 `edit.concat.transition` は実際の video-editing-skill の enum（15種類）に対して検証し、`"none"` を含む未知の値は planning 時点で拒否する。合わせて、より大きな同種の欠陥（`edit./audio./subtitle/thumbnail/color./motion./qc` 名前空間全体で未知のサブキーが無音で無視される問題）を発見したが、安全な修正範囲を確定できず今回は見送る（実データ検証、2026-09-07、PR #47）
- 事実: ユーザー提供の実サンプル5本（すべて音声トラックなし）を実際に `video-agent plan`/`render` に通す検証の一環で、`--set edit.concat=true --set edit.concat.transition=none` を試したところ、plan は何のエラーも無く `APPROVED` になったが、`render` は `video-editing/concat` への `INVALID_ARGS`（`video-editing [INVALID_REQUEST] project.operations[0].transition.type: must be one of [...]`）で `FAILED` した。`editing.py` のモジュール docstring 自身が「An invalid value is refused at planning time (ValueError) — nothing is corrected or guessed」と明言しているにもかかわらず、実際には `_TRANSITION_RE = re.compile(r"^[a-z]{1,16}$")` という「小文字1〜16文字」という緩い正規表現しか使っておらず、video-editing-skill の実際の enum（`fade`/`dissolve`/`wipeleft`/.../`radial` の15種類、`contract.py` 内に列挙）を一切検証していなかった。兄弟キー `edit.concat.mode` は同じ関数内で `re.compile(r"^(pad|crop)$")` という正しい enum 検証を既にしており、`transition` だけが取り残されていた（見落としであって設計判断ではない）。`"none"` は ffmpeg-skill 自身の生 CLI（`--transition none`）にだけ存在する語彙で、video-editing-skill 経由でトランジション無しの直接カットを求める正しい方法は `edit.concat.transition` キー自体を省略することだと `video-editing-skill/contract.py`（`"transition": "... (optional)"`）で確認した。
- 決定: `_TRANSITION_RE` を実際の15種類の enum（`_TRANSITIONS` として明示的に列挙、video-editing-skill 自身のパッケージを import せず、ここに pin する——ADR-001 以来の「Skill は import せず境界越しに扱う」原則どおり）に対する正規表現へ差し替え。エラーメッセージも `edit.concat.mode`/`edit.overlay.position` と同じ「one of ...」形式に統一。これにより `edit.concat.transition="none"` や他の任意の未知の値は、render まで進む前に plan 時点で `EditRequirementError` として明確に拒否されるようになった。
- 発見したが対象外とした、より大きな構造的欠陥: 上記の調査の過程で `--set subtitle.generate=true`（`subtitle.generate` は内部の decision subject 名であり、正しい実際のスイッチは裸の `subtitle`）を試したところ、`service.py` のトップレベル prefix チェック（`k.startswith(REQUIREMENT_PREFIXES)`、"subtitle" は許可 prefix）は通過し、`agent/subtitles.py` の `parse_subtitle_requirements()` は `m.get("subtitle")` が `None` のため何もせず黙って `enabled=False` を返し、結果として plan は字幕に一切触れず `APPROVED` になった——エラーも警告も無い、完全な無音の無視だった。この欠陥は `subtitle.*` に限らず、`edit./audio./thumbnail/color./motion./qc` の全ての名前空間で構造的に同じ（各パーサーは自分が知っているキーだけを `m.get()` で読み、知らないキーの存在自体をチェックしない）。実際に「既知の全キーの網羅的な allowlist」を組んで `service.py` に unknown-key 検証を追加してみたところ、`tests/test_unit.py` で当初 21 件、`REQUIREMENT_KEYS`/`COLOR_KEYS`/`MOTION_KEYS`/`THUMBNAIL_KEYS`/`qc` を網羅した後も残り 18 件が失敗し続けた——原因は `<subject>.approval`（`decision.py`/`decision_finishing.py` の `APPROVAL_KEYS` の値側）、および `audio.loudness.target_lufs`/`audio.loudness.true_peak`（`agent/audio.py` の外、`decision.py` に直接ハードコードされ、`agent/requirements.py` の自由文書キーワード抽出にも別途登場する、ADR-030 以前からの一般的なラウドネス正規化語彙）という、どの `REQUIREMENT_KEYS` 系定数にも載っていない、正当だが分散した第三・第四の語彙群だった。この時点で「本当にこれで全部か」を確信できる保証が無く、誤ってこれ以上の正当なキーを拒否してしまうリスク（無音の無視より悪い、動いていたワークフローを壊す回帰）の方が高いと判断し、`service.py` 側の変更は全て revert した。
- 対象外（今回は意図的に見送り、将来のための記録）: `edit./audio./subtitle/thumbnail/color./motion./qc` の全名前空間にわたる「未知のサブキーを無音で無視しない」修正そのもの。正しくやるには、`decision.py`/`decision_finishing.py`/`agent/requirements.py` を含む全ての `m.get("...")` 呼び出しを網羅的に洗い出し、各文字列が (a) `--set` で正当に設定可能な requirement キーなのか、(b) 内部専用の decision subject 名なのか、(c) `rules`/profile 経由でのみ設定される policy キーなのかを1つずつ確定させる必要があり、それは本 PR の一発の変更で片付けられる規模ではない。`WORK_QUEUE.md` に評価済みの事実として記録し、次のセッションが `git stash`/`git diff` 無しにここから再開できるようにする。
- 保証: `editing.py` の変更は additive/修正のみ（`_TRANSITIONS` は video-editing-skill の既存 enum の写しであり、新しい語彙の追加ではない）。`tests/test_unit.py`: 210 passed（新規ケース2件 `edit.concat.transition="none"`/`"xyzzy"` が `EditRequirementError("... one of ...")` になることを確認）。`tests/test_integration.py`（実 ffmpeg + 実9 Skill、モック無し）: 48 passed, 0 failed。実データでの実行確認: `--set edit.concat=true`（`transition` 省略）でユーザー提供の実サンプル5本（音声トラック無し、ADR-041 の `join.py` 修正が効く条件）を実際に concat → `COMPLETED`, QA PASS, 82.05秒の 1920x1080 H.264 を実際に生成して確認。

## ADR-043 ADR-042 で見送った「`edit./audio./subtitle/thumbnail/color./motion./qc` の未知のサブキーが無音で無視される」問題を、今度は網羅的な調査の上で修正する（実データ検証の続き、2026-09-07、PR #48）

## ADR-047 `audio-production`/`color-grading`/`video-editing` の contract drift を fatal / non-fatal に分類し、後方互換な Skill バージョンアップだけで capability が MISSING に落ちる回帰を構造的に止める（2026-09-10、PR #54 に続く2回目の同種回帰の再発防止）
- 経緯: 同一セッション内で `audio-production-skill`/`color-grading-skill`/`video-editing-skill` がそれぞれ2回ずつバージョンを上げ（機能追加のみ、破壊的変更なし）、その都度 `Service.caps.resolve()` が該当 Skill を `MISSING` と報告する回帰が発生した（1回目: PR #53、2回目: PR #54）。両方とも原因は同じで、`SUPPORTED_SKILL_VERSIONS`（バージョン文字列 prefix のタプル）を広げ、`PINNED_CONTRACT_PATH` のスナップショットを新バージョンのものに差し替えるまで、`contract_drift()` が「pinned スナップショットと live contract の差分」を無条件に検出し続け、`capabilities/resolver.py` の `ok = doctor_status in ("ok","degraded") and not drift`（3箇所: `video-editing`/`audio-production`/`_finishing_skill` 共通コード）が非空の drift を無条件に fatal 扱いしていたことだった。ユーザーから「それぞれのバージョンが単独で上がっても連携が途絶えない方法はあるんじゃないの？」と問われ、再発防止のための恒久対応に着手した。
- 事実: `contract_drift()` が比較する `DRIFT_KEYS`/`DRIFT_OPERATION_KEYS`（Skill ごとに `DRIFT_TOOL_KEYS`/`DRIFT_ELEMENT_KEYS` 等の名前で存在）には、性質の異なる2種類のフィールドが無区別に混在していた。(1) **プロトコル形状フィールド**（`schema`/`skill_id`/`kind`/`execution`/`request`/`response`/`provenance`/`schema_versions`/`errors` 等）: これが変わると実際に危険——エンジン設定・禁止フィールド・エラー語彙といった、アダプタがハードコードで前提にしている安全境界そのものが変わったことを意味する。(2) **追加的な容量拡大フィールド**（`version` 自体、新しい operation/tool の出現、既存 operation の `parameters` が新しい任意パラメータを獲得すること、`unsupported_operations`/`output_formats` が縮小・拡大すること）: これらは実行時の挙動を一切壊さない——`params_for()`/`build_request()` 系のロジックは常に pinned スナップショットではなく **live contract** を直接読んで検証しているため、pinned スナップショットが古いままでも実際の呼び出しが誤った検証をすることは原理的に起こらず、単に「このアダプタがまだ知らない新機能がある」という情報でしかない。`tools`（この3 Skill では実行ツールが1個だけの配列）についても、その要素が持つ `role`/`produces_output`/`deterministic` 等の不変条件は `check_contract()` が live contract に対して毎回独立に強制しており、`tools` 自体を drift の fatal 対象に含めるのは冗長だった。
- 決定: `tools/skill_process.py` に共有ヘルパー `breaking_drift(live, pinned, fatal_keys, list_key, item_id, fatal_item_keys)` を追加。既存の `drift_report()`（全差分、可視化用、非変更）とは別に、fatal と宣言されたキーだけを比較し、リストメンバーシップは「pinned にあるのに live から消えた」場合のみ fatal（既に依存している能力が失われた）、「live にだけ新しく現れた」場合は非 fatal（まだ使っていない新機能）として扱う。`audio_production`/`color_grading`/`video_editing` の各 `adapter.py` に `FATAL_DRIFT_KEYS`/`FATAL_DRIFT_(OPERATION|TOOL)_KEYS`（= 既存の `DRIFT_KEYS`/`DRIFT_*_KEYS` から `version`/`unsupported_operations`（`unsupported`）/`output_formats`（`formats`）/`tools`/`parameters` を除いたもの）と `contract_breaking_drift()`、アダプタに `breaking_drift()` メソッドを追加。`capabilities/resolver.py` の3箇所（`video-editing`/`audio-production`/`_finishing_skill` 共通コード）を `not drift` → `not ad.breaking_drift()` に変更（`_finishing_skill` は `hasattr(ad, "breaking_drift")` で分岐し、まだこの対応をしていない `motion-graphics`/`qc`/`subtitle`/`thumbnail` は従来通りの厳格な全 drift gating を維持——一律の書き換えは今回の実証済み範囲を超えるため見送り）。`evidence["drift"]` は引き続き全差分（`drift()`）を保持し、可観測性は一切失わない——変わるのは「何を可視化するか」ではなく「何が capability を MISSING に落とすか」だけ。`SUPPORTED_SKILL_VERSIONS`（バージョン文字列 prefix によるゲート）自体は意図的に変更していない: `ffmpeg_skill/locate.py` の `SUPPORTED_MAX_EXCLUSIVE` に既にある規律（「widening this needs a verified integration run, not a silent edit」）と同じ理由で、未検証のバージョンを無条件に許可する変更はこのリポジトリの既存方針（`check_contract()` 各所の "Anything off is refused, never patched" docstring）に反する——今回の対応後も、Skill のマイナーバージョンを上げた際は `SUPPORTED_SKILL_VERSIONS` を1行広げて検証する手順は変わらないが、その後 pinned スナップショットを都度リネーム・再生成する必要は追加的な変更に限ってはなくなる。
- 検証: 3 Skill それぞれについて、pinned contract を複製してバージョンを上げ・任意パラメータを追加・`unsupported_operations` を縮小した合成 live contract で `contract_breaking_drift()` が `[]` を返すこと、逆に依存中の operation/tool を削除した場合と `execution.shell=True` にした場合は非空を返すことを直接確認（`tests/test_unit.py::VideoEditingAdapterTests/AudioProductionAdapterTests::test_breaking_drift_classification`、`tests/test_adapter_color_grading.py::ColorGradingAdapterTests::test_breaking_drift_classification`、新規6テスト）。各アダプタの既存の「compatible だが drift した contract」フェイクテスト（`FAKE_{CG,AP,VE}_MODE=contract_drift`）にも `ad2.breaking_drift() == []` の確認を追加。`AudioProductionPathTests::test_capability_verdicts_unknown_is_not_available`（resolver 経由、実際に `CapabilityResolver.resolve()` を呼ぶ唯一の drift 回帰テスト）を、旧仕様（`contract_drift` モードで `MISSING` になる）から新仕様（`AVAILABLE` のまま、detail に drift 情報は残る）へ更新。`tests/test_unit.py` + `tests/test_adapter_color_grading.py`: 259 passed, 3 skipped（環境依存の既知失敗はゼロ）。`tests/test_integration.py`（実 ffmpeg-skill + 実 audio-production-skill + 実 color-grading-skill + 実 video-editing-skill、モック無し）: 全件通過を確認（実行ログは PR 本文参照）。
- 対象外: `motion-graphics`/`qc`/`subtitle`/`thumbnail` への同様の fatal/non-fatal 分類の適用——この4つは本セッション中に同じ回帰を実際に起こしていない（バージョン変更なし）ため、今回検証した3 Skill に限定し、将来これらがバージョンを上げて同じ問題が起きた時点で同じパターンを適用する。`SUPPORTED_SKILL_VERSIONS` の tuple-of-prefix 表現を `ffmpeg_skill/locate.py` と同じ semver min/max-exclusive 形式に変換すること——検討したが、`"0.3."` のような prefix 表現は既にパッチバージョンの吸収を無条件にサポートしており、マイナーバージョンごとに1行足す/変える手間は表現を変えても解消しないため、見た目の統一以上の実益がないと判断し見送った。video-production-agent への自動 CI トリガー追加——`.github/workflows/tests.yml` の `workflow_dispatch` 限定は Actions 分数制約による既存の意図的な決定であり、今回のスコープ外。
- 保証: 全て additive（新しいヘルパー関数・新しい定数・新しいメソッド・resolver 内3箇所の gating 条件変更のみ）。`drift()`/`contract_drift()` の戻り値・意味は完全に不変——既存のどのコードもこれらの可視化目的の利用に影響を受けない。`SUPPORTED_SKILL_VERSIONS` によるバージョン受け入れゲート自体（あるいは `check_contract()` のどの検証も）は一切変更していない。`tests/test_unit.py` + `tests/test_adapter_color_grading.py`: 259 passed, 3 skipped。`tests/test_integration.py`: 実 Skill 4種（ffmpeg-skill/audio-production-skill/color-grading-skill/video-editing-skill）に対して全件通過。

## ADR-048 衛星 Skill のエンジン互換性は Skill 自身の capability detection に任せ、ffmpeg-skill の改名フラグは実物の `--help` で選ぶ。ADR-047 の fatal / non-fatal 分類を motion-graphics / subtitle / thumbnail / qc に広げる（2026-10-29）
- 事実: 2026-10-29 時点で `video-agent doctor` は ffmpeg-skill 2.20.0 を DEGRADED、video-editing / audio-production / subtitle / thumbnail / color-grading / motion-graphics を MISSING と報告し、実 Skill 統合テストは 24 件失敗していた。原因は3つ。(1) 衛星 Skill が ffmpeg-skill との互換性の宣言を固定の `version_window` から capability detection（使う tool と flag を実際の ffmpeg-skill の contract / `--help` で検出し、自分の doctor で報告する。各 Skill の ADR-18/19 等）に移し、`ffmpeg_skill` / `engine` ブロックの形が変わった。agent はこのブロックを fatal drift として固定しており、`check_contract()` は `version_window` を必須にしていた。(2) ADR-047 で対象外にした motion-graphics / subtitle / thumbnail / qc には fatal / non-fatal の分類が無く、説明文の変更（subtitle の operation `description`）や純粋な追加（motion-graphics 0.2.0 の hook / meme / sticker、`provides`）だけで MISSING に落ちていた。(3) ffmpeg-skill 1.10 で再エンコード系 tool の `--crf` が `--quality`（同じ CRF スケール）に改名され、2.x は `--crf` を拒否する（`export.py` は `--crf` のまま）。agent の catalog は `--crf` を出していた。audio-production 0.4.0 は operation / request / response が 0.3.0 と同一で、`SUPPORTED_SKILL_VERSIONS` の外だっただけ。
- 決定: `tools/skill_process.py` に `engine_compat_errors()` / `engine_compat()` を追加し、`ffmpeg_skill` の宣言は `version_window` か `compatibility` のどちらかがあれば受け入れる（どちらも無い contract は従来どおり拒否）。エンジン互換性は Skill 自身が検出し doctor で報告し、resolver はその doctor が ok であることを既に要求しているので、`ffmpeg_skill`（audio / color / motion / thumbnail）と `engine`（video-editing。`engine.id` は `check_contract()` が引き続き検証）を fatal drift から外す。motion-graphics / subtitle / thumbnail / qc に `contract_breaking_drift()` と `breaking_drift()` を追加: 共通して `version` は non-fatal、subtitle は operation の `description` を比較から除外、motion-graphics は `unsupported_*`・`tools`・`request`（依存する部分は `check_contract()` が毎回検証する）を non-fatal にし、既に固定している element type のキーは fatal のまま。ffmpeg-skill の `crf` は、インストールされた script の `--help` が `--quality` を出していればそれを、無ければ `--crf` を使う（`FfmpegSkill.offers_flag()`、script ごとに1回だけ読む）。この上で ffmpeg-skill の受け入れ範囲を `< 3.0.0` に広げ、audio-production の `SUPPORTED_SKILL_VERSIONS` に `0.4.` を足し、6 Skill の pinned contract を現在の live contract に更新した。加えて、ffmpeg-skill 2.x の `loudness.py --measure-only` は loudnorm の値を `measured` の下に入れるようになり、agent は値を読めず `lufs: null` の観測を「許容範囲内」と判定していた（計測していないのに AUTO で KEEP）。`MediaAnalyzer._shape()` は両方の形を読み、数値の無いラウドネス観測は「許容範囲内」とは言わず CONFIRM（再計測を促す）にした。
- 決定（品質検査）: QA のラウドネス判定も、数値の無い計測を PASS（"measured only"）にしていた。共通の読み取り `loudness_facts()` が `measured` を展開し、数値の無い計測は WARN にした。ffmpeg-skill 2.x の他の挙動変更に合わせて統合テストの期待値を直した: `check --platform youtube` が字幕トラックの無い納品物に WARN を出す（正しい指摘なので、テストはこの1項目だけを許容し、他の WARN / FAIL は従来どおり失敗）、`fit.py` の aspect のみ指定は元の解像度を超えて拡大しない（640x360 → 1:1 は 360x360）、audio-production 0.4.0、transcription-skill の `transcription/batch` 追加。
- 検証: `video-agent doctor` で 10 Skill すべて AVAILABLE（ffmpeg-skill 2.20.0、各衛星は origin/main）。unit（`tests/` から integration を除く）: 397 passed, 10 skipped。`tests/test_integration.py`（実 Skill・実メディア、faster-whisper base モデルあり）: 53 passed（修正前は 24 failed / 14 passed / 15 skipped）。`evals/run.py`: 94/99 で、失敗5件（`plan_no_audio_no_silence_step` と `ve_*` 4件）は修正前と同一。
- 対象外: ffmpeg-skill の受け入れ範囲そのものを capability detection に置き換えること（agent は ffmpeg-skill の script を直接呼ぶので、範囲は「統合テストで確かめた版」の記録として残す）。各衛星 Skill の contract が報告する `version` が pyproject より古い問題（Skill 側のリリース自動化の問題）。

## ADR-050 チャットのモデル（Claude Code / Claude Desktop）を脳にする host provider と MCP server。API キー無しで AI 推薦を使う（2026-10-30）

## ADR-051 インストールされていないスキルの工程は handoff として名指しする。エージェントは自分の仕事として扱わない（2026-10-30）
- 事実: スキルは単体でも使われており、全スキルがそろっている前提は成り立たない。既存の動作では、その環境で tool を選べない工程は step の `tool` が空になり、plan が BLOCKED になる（`production_plan.py`）。理由は `video-agent skills` を別に見ないと分からず、チャットのモデル（ADR-050）には「何が足りず、どうすれば進むか」が渡っていなかった。
- 決定: `Service.handoffs(ir)` は、tool の無い工程ごとに次の項目を返す。

## ADR-053 同じセリフの複数テイクから最良テイクを測定値だけで選び、セリフ順に組み、音楽のビートにつなぎ目を合わせる（take selection、2026-10-30）
- 事実: 同じセリフを何度か撮ると、似たクリップが入力に並ぶ。agent はこれまで、入力をすべて（`edit.concat`）か入力ごとに扱うだけで、どのテイクを使うかを決める decision が無かった。使える測定は transcript（transcription-skill の segments / text）、loudness（integrated LUFS / true peak）、silence の3つ。sharpness / exposure を測る adapter は無い（media-analysis-skill 0.1 に該当 tool が無い）。顔検出も無い（detection-skill は agent に接続されていない）。ffmpeg-skill 2.21 の `scenes.py --beats --json` は `beats`（時刻）と `beat_grid`（tempo_bpm / interval / phase / confidence / supported_beats / usable …）を返す。120 BPM のクリックトラックの実測で、`supported_beats` は 0.5 秒刻みの 20 点、confidence 0.979 だった。食い違いが2つある。(1) `scenes.py` は video stream の無い入力を `input has no video stream` で拒否するので、wav / m4a の音楽はそのまま測れない。(2) `cut.py --snap beats --snap-source` は cut する source の時刻を grid に寄せる。複数テイクを並べた programme では、つなぎ目の位置は programme 上の時刻（それまでの pick の長さの和）なので、source の時刻を寄せてもつなぎ目はビートに乗らない。
- 決定: 次の requirement を足す（明示の `--set` だけ）。
  - `edit.takes`（true: 音楽以外の video 入力はすべて、どれかのセリフのテイク）
  - `edit.takes.similarity`（0.3–1.0、既定 0.6）
  - `edit.takes.music`（音楽の入力 index。その入力の beat grid を測り、つなぎ目を合わせる）
  - `edit.takes.snap_max_shift`（秒、0.01–2.0、既定 0.5）
  refinement だけの指定、範囲外の値、存在しない index は解析前（index は decision 時）に拒否する。`agent/takes.py` は次を決定的に行う（AI は使わない）。
  - **グループ化**: segments を連結し、NFKC・小文字化・つなぎ言葉の除去・非単語文字の除去をした文字列どうしの `difflib.SequenceMatcher` ratio（autojunk off）を比べる。入力順に、各セリフの最初のテイクとの ratio が閾値以上で最大のセリフに入れる（同点は先のセリフ）。どれにも届かなければ新しいセリフにする。セリフ順は入力に最初に現れた順。
  - **採点**: 100 から減点する。どの減点も、読んだ observation の id と値を残す。
    - つなぎ言葉: 8 × 個数（transcript）。日本語は「えーと / えっと / えー / あのー / そのー / うーん / んー」、英語は um / uh / er / erm / ah / hmm。あの / その / まあ は普通の語でもあるので数えない。
    - 言い直し: 15 × 回数。直後に同じものを繰り返した箇所を数える。単語の文は 1–3 語、CJK は 3–10 文字。つなぎ言葉は無視する。
    - 欠け: 50 ×（セリフの代表テイク〔他のテイクとの類似の和が最大のもの〕のうち、言っていない割合）。
    - クリップ: true peak が -0.1 dBTP 以上なら 30。
    - 間: 4 × 話している区間の中の無音の秒数。
    - 音量: 2 ×（セリフの中央値から 3 LU を超えて離れた LU）。
    sharpness / exposure / faces は採点しない（測る adapter が無い）。その旨と理由を pick ごとに `unmeasured` として残す。
  - **選択**: 得点の高い順、同点は入力の早い順。decision は `takes.pick`（TRANSFORM、セリフごとに1つ、policy `takes.pick.approval`、既定 CONFIRM。どのテイクを捨てるかは編集判断なので、`edit.takes` で waive しない）。params には全テイクの得点・要因・順位、`deterministic_pick`、`keep`（話している区間 ± 0.15 秒、source の中に収める）、`unmeasured` を入れる。
  - **AI**: AI 推薦（intent `take_selection`。`edit.takes` があるときだけ allowed_intents に入る。ADR-018 の検証を通り、記録済みの observation を引用したものだけ）がセリフ内の1テイクを名指しした場合は、それを pick にする。得点は測ったまま変えず、理由に両方を書き、provenance を AI_GENERATED、承認を CONFIRM 以上にし、推論 id を evidence に足す。引用の無い推薦は ai_reasoning で捨てられる。1つのセリフで複数のテイクが名指しされた場合は採点順を使い、名指しは REVIEW 項目に残る。
  - **組み立て**: pick をセリフ順に入力とする `video.concat`（`edit.concat` と同じ操作・同じ plan 経路）を作る。concat の step と operation は pick も引用するので、pick を REJECT すると組み立ては rejected-cited になる。選ばれなかったテイクと音楽には decision も step も作らない。pick には silence.leading / trailing / internal の削除を作らない（範囲は pick 自身が決め、間は減点に入れる）。
  - **ビート合わせ**: 解析 kind `beats`（SkillSpec `beat_analysis` → `ffmpeg-skill/scenes --beats`、catalog に `beats` フラグ）を足す。`beat_input` で指定した入力だけを測り、他は SKIPPED にする。decision は `takes.beat_snap`（TRANSFORM、policy `takes.beat_snap.approval` 既定 CONFIRM、`edit.takes.music` が明示なので AUTO）。音楽を programme 時刻 0 から敷く前提で、各 pick の out 点を `snap_max_shift` 以内で最も近い supported beat に動かす（同距離なら早い方）。最後の語の 0.05 秒後より前と、source の終わりより後には動かさない（届かない out 点はそのまま残し、理由を書く）。計算は agent が programme 時刻で行う（上の食い違い (2) のため、`cut --snap` は使わない）。合わせた trim は frame-accurate にする。測定が無い場合（音声だけの音楽を `scenes.py` が拒否した場合を含む）、usable が偽の場合、confidence 0.5 未満の場合は BLOCK。
  - validator は次を検査する。pick の範囲が source の中にあること。pick が自分の採点表にあること。concat の入力が pick のセリフ順と一致すること。合わせたつなぎ目が、記録済みの beat 測定の supported beat にあり、trim の長さの累積（実際の cut list）もそこで終わること。
  タイムライン書き出し（ADR-052）は、この cut list から変更なしで動く。
- 検証: `tests/test_takes.py`（19件）。つなぎ言葉 / 言い直し / 類似 / 欠けの計算、入力が交互でもセリフ順にまとまること、要因ごとの evidence と同点の順、測定の無い要因を作らないこと、programme 時刻でのビート合わせ（語を切らない、source を越えない、同距離は早い方）、requirement の拒否を確かめる。plan 側では、2セリフ × 3テイクで期待どおりの pick になり、選ばれなかったテイクに step が無く、concat がセリフ順で、render と OTIO の clip が pick と一致すること、ビートの測定が音楽だけにあり、つなぎ目が beat 上に乗り、改ざんした trim / join を validator が拒否すること、音声だけの音楽と低 confidence の BLOCK、concat 併用と無音テイクの BLOCK、1セリフなら pick 単体で納品されること、pick の REJECT で組み立てが rejected-cited になること、AI の上書きでは得点が変わらず CONFIRM / AI_GENERATED になること、引用の無い AI・名指しが割れた AI では何も変わらないこと、`scenes --beats` の argv を確かめる。`evals/cases/103`–`107`（107/107）。103 は1テイク目が言い直し、2テイク目がクリップで、3テイク目が選ばれる。104 は2つのつなぎ目が実測ビート上に乗る。`tests/test_integration.py::BeatGridRealTests`（実 ffmpeg-skill 2.21）: 黒画面 mp4 に入れたクリックトラックを tempo 120 ± 1 BPM、confidence 0.5 以上、0.5 秒格子上の supported beat 15 点以上と測り、テイク側の入力は SKIPPED になる。
- 対象外（次の段階）:
  - つなぎ目の音声クロスフェード。audio-production の `concat` crossfade は音声だけの経路で、n 本をつなぐと音声が (n-1)·d 短くなる。hard cut の絵と合わせるには、音声側に重なり分の handle を足すことと、音声を絵に mux する工程が必要で、どちらもまだ無い。→ ADR-054 で対応。
  - 音楽をミックスに入れることと、タイムラインに音楽トラックとして載せること（render.py の project は music を持てるが未接続）。
  - 音声だけの音楽ファイルの beat 測定（ffmpeg-skill 側で `scenes.py --beats` が音声入力を受けること）。
  - sharpness / exposure / 顔の採点（測る adapter ができてから）。
  - pick の手動差し替え（今は REJECT すると組み立てが止まる）。

## ADR-054 テイクの組み立てのつなぎ目に音声クロスフェードを入れる。絵の cut 点と長さは動かさず、音声に handle を足して mux し、A/V 同期を validator で確かめる（2026-10-30）
- 事実: ADR-053 の組み立ては絵も音も hard cut で、つなぎ目で波形が不連続になり、クリック音が出ることがある。audio-production-skill 0.4.2 の `CONCAT` は `crossfade`（秒、0–30、ffmpeg `acrossfade`）を持つが、各クリップを前のクリップの終わりの `crossfade` 秒前から始めるので、n 本をつなぐと合計が Σ − (n−1)·crossfade になる（`timeline.py` の `concat`）。crossfade は1つの値で全つなぎ目にかかり、どの入力も crossfade より長くなければならない（`INVALID_TIME_RANGE`）。入力は 2–32 本。ffmpeg-skill 2.21 の `audio.py --replace FILE` は音声を差し替え、絵は stream copy、新しい音声は `apad,atrim` で絵の長さに合わせる（絵を短くしない）。video-editing の `cut` を keyframe 精度で使うと、絵の始まりが keyframe にずれる。
- 決定:
  - requirement `edit.takes.crossfade`（秒、0.0–0.1、既定 0.010、0 で無効）を足す。`edit.takes` 無しの指定・範囲外は解析前に拒否する。既定の 10 ms は出典のある値ではなく、ここで選んだ既定値。理由: butt join の段差はどんな短いランプでも消える。10 ms は 100 Hz の1周期で、話し言葉の音節よりずっと短いので、2つの語を混ぜて聞かせない。
  - 計算（`agent/takes.py::plan_crossfades`、beat snap の後の cut list に対して）: 各つなぎ目で、出ていく pick の音声を絵の out 点の後へ `out_handle`、入ってくる pick の音声を絵の in 点の前へ `in_handle` 延ばし、`out_handle + in_handle = crossfade` にする。両側に余裕があれば半分ずつ（crossfade は cut の中心に乗る）。片側が足りなければ、もう片側が残りを持つ（同期は保たれ、中心からは外れる）。2つの source の余裕の和が crossfade に満たないつなぎ目と、crossfade 以下の長さの pick に接するつなぎ目は hard cut のままにし、理由（各側の余裕の秒数）を join に書く。こうすると、各 pick の音声は、programme 上で絵の始まりのちょうど `in_handle` 前から始まり、最後の音声は絵と同時に終わる。音声の長さは Σ(span) − Σ(crossfade) = 絵の cut list の長さになる。絵の cut 点（beat に合わせたものを含む）は動かさない。
  - decision `takes.crossfade`（TRANSFORM、risk LOW、policy `takes.crossfade.approval` 既定 AUTO。何が映り何が話されるかは変えず、段差を短いランプに置き換えるだけなので）。params に全つなぎ目（at、各側の余裕、handle、crossfaded、hard cut の理由）、pick ごとの span（絵の範囲・音声の範囲・handle・programme 上の開始）、run、programme と音声の長さ、同期の許容差を入れる。既定値なら provenance SYSTEM、明示なら USER。どのつなぎ目にも余裕が無い場合、pick が 32 本を超える場合、既定値なのに audio-production（CUT / CONCAT）か mux の道具がこの環境に無い場合は KEEP（hard cut の音声のまま、何も計画しない）にし、理由を書く。明示の `edit.takes.crossfade` が実行できない場合は BLOCK（capability.*）にする。黙って捨てない。
  - 計画（planner）: video.concat の直後に、(1) pick ごとに source から span を切り出す audio-production `CUT`（skill `audio_cut`、span の外を remove）、(2) crossfade でつながる pick の並び（run）ごとに `CONCAT`（crossfade あり）、run が複数なら run どうしを `CONCAT`（crossfade 0、つまり hard cut）、(3) 新しい skill `audio_mux`（tool `ffmpeg-skill/audio`、`--replace` だけを catalog に載せる）で、組み立てた絵の音声を programme 音声に差し替える。後の工程（loudness / 書き出し / QC）は mux の出力に続く。crossfade する pick の trim は frame-accurate にする（音声は sample 単位で切るので）。IR は `audio.take_crossfade`（spans / joins / concats / audio / mux / timeline_duration / decision_ids）に記録し、`audio.operations` には入れない（音声だけの経路の検査と混ざらないように）。REJECT された crossfade は rejected-cited になる。OTIO の書き出し（ADR-052）は絵の cut list なので変わらない（hard cut のまま）。
  - validator（`check_take_crossfade`）は decision の計算を信じず、IR から作り直して確かめる: span の絵の範囲が video.trim の keep と一致し（cut list が動いていない）、trim が frame-accurate であること。span の音声が source の中にあり、絵の範囲 + handle であること。CUT の remove が span の外のすべてであること。最初の pick に in_handle、最後の pick に out_handle が無いこと。各つなぎ目で handle の和がその crossfade（または 0）であり、hard cut には理由があること。記録された CONCAT を audio-production の算術（各入力は前の入力の終わりの crossfade 前から始まる）で再生し、各 pick の音声の開始 + in_handle が、cut list から求めた絵の開始と 1 ms 以内で一致すること（`SYNC_TOLERANCE`。ITU-R BT.1359-1 の検知閾 +45 ms / −125 ms よりずっと小さく、IR の丸めだけを吸収する）。音声の長さ、cut list の長さ、record の timeline_duration が組み立てた絵の長さと一致すること。mux が programme 音声を組み立てた絵の下に入れること。decision があるのに record が無い場合もエラーにする。
- 検証: `tests/test_takes.py`（29件、うち10件が本 ADR）。中心に乗る handle / 片側だけの余裕 / 余裕の無いつなぎ目と短い pick の hard cut、各 pick の音声が絵と同時に始まり音声が絵と同時に終わること、requirement の既定と拒否。plan 側では、既定で decision（AUTO / SYSTEM）・3つの span・2つの CONCAT（0.01 → 0）・mux が計画され、crossfade 0 の計画と cut list が同じで、trim が frame-accurate になること。validator が handle の改ざん（同期のずれを ms で報告）、cut の移動、keyframe 精度、mux の差し替え、crossfade 値の改ざん、record の欠落を拒否すること。render で audio-production の 5 回と mux が concat の後・loudness の前に走り、provenance に crossfade の decision が残ること。beat に合わせた cut 点が crossfade の有無で同じこと。余裕が無い / audio-production が無い場合は KEEP、明示なら BLOCK。REJECT で rejected-cited。`evals/cases/108`–`112`（112/112）: 108 は3セリフで、つなぎ目1が crossfade、つなぎ目2が余裕無しで hard cut に戻る。109 は beat 合わせ + 明示 0.02 s。110 は audio-production 無しの既定で KEEP、111 は明示で BLOCK、112 は範囲外で拒否。`tests/test_integration.py::TakeCrossfadeRealTests`（実 ffmpeg-skill / video-editing-skill / audio-production-skill。音声認識だけ sidecar transcript を読む fake）: 各テイクの既知の時刻に入れた 1 kHz のバーストが、納品ファイルで絵の示す時刻から 1 ms 未満の差で見つかり、音声と絵の長さが一致する。つなぎ目2は hard cut に戻る。
- 対象外（次の段階）:
  - crossfade の曲線の指定（audio-production `CONCAT` は曲線を受け取らず、ffmpeg `acrossfade` の既定を使う）。
  - 32 本を超える pick の crossfade（CONCAT の入力上限。入れ子にすればできるが、今は KEEP）。
  - frame の量子化による残り（frame-accurate の cut は各 cut 点を frame に置くので、cut list の秒が frame の境目に無いと、各端で最大半 frame の差が残る。累積を避けるには cut list を frame に揃える必要があるが、beat に合わせた cut 点を動かさないため、ここではしない）。
  - OTIO への音声 crossfade の書き出し（タイムラインは絵の hard cut のまま）。

## ADR-056 ffmpeg-skill の手書き catalog を、locate 時に Skill 自身の contract（`_contract.py --json --static`）と doctor で照合する。改名・削除されたフラグはその tool だけを理由付きで unavailable にし、実行時の argparse エラーにしない（ECOSYSTEM_ROADMAP step 3、2026-10-30）
- 事実: agent は ffmpeg-skill の 20 script を `tools/ffmpeg_skill/catalog.py` の手書き catalog（script ごとに emit する flag・型・positional）で呼ぶ。照合は integration test の `--help` 文字列検索だけで、実行時には何も確かめていなかった。フラグが改名されると、plan は通り、render 時に script の argparse が `unrecognized arguments` で落ちる。ffmpeg-skill は 0.9.0 から `scripts/_contract.py --json --static`（`contract_version` 1.0、tool ごとの `input_schema` は argparse parser から生成され、`properties[*].cli` に実際の綴り、`type` に switch なら `boolean`、`positional` / `required`）と `_contract.py doctor --json`（tool ごとの `usable: yes|no|unknown`、`missing`、`fix`。exit 1/2 でも document を出す）を出している。2.22.1 の main で catalog の全 flag・switch の arity・positional は contract と一致する。
- 決定:
  - `tools/ffmpeg_skill/contract_check.py`: `check_catalog(contract, doctor, scripts)` は純関数。`contract_version` の major が 1 でない、`skill.id` が `ffmpeg-skill` でない、document でない → package 全体を `refused`（どの事実も信用できない）。それ以外は catalog の tool ごとに、tool が publish されているか、catalog が emit しうる各 flag（`FLAG_ALIASES`、`crf` は ADR-048 どおり `--quality` か `--crf` のどちらか）と adapter が付ける `--json` / `--dry-run` が `input_schema` にあるか、catalog の `bool` ⇔ contract の `boolean`（switch が値付き flag になった・その逆）、catalog の positional が contract の positional の先頭と一致し残りが required でないか、を確かめ、外れた tool だけを理由付きで unavailable にする。数値型（int / float）の違いは見ない（adapter は `%g` で渡し、既存の組み合わせが動いている）。
  - doctor を表に出す: catalog の tool で doctor が `usable: no` なら、doctor 自身の `missing` と `fix` を理由に unavailable。`unknown` は「検出できなかった」であって欠落ではないので止めず、`evidence.contract.doctor` に記録する。doctor が document を出さない時は note を残し、contract の結果だけで判断する。
  - `FfmpegSkill.catalog_check()` が checkout と version ごとに 1 回だけ読み（cache）、`locate_ffmpeg_skill` が見つけた時点で読む。`scripts/_contract.py` が無い checkout（0.9.0 未満、`SUPPORTED_MIN` 0.8.4 の範囲内）は `unchecked` として従来どおり catalog を使い、doctor の detail にそう書く。
  - 理由の経路は既存の capability 機構に乗せる: ToolSpec の `required_capabilities` に tool ごとの capability `ffmpeg-skill:<tool>` を足し、resolver（`ffmpeg_skill_capabilities`）がそれを AVAILABLE / MISSING（`evidence["reason"]` に理由）にする。`refused` は package capability `ffmpeg-skill` を MISSING にする。`SkillRegistry.select_tool` は missing capability に `evidence["reason"]` があればその文を理由に含めるので、`video-agent skills`、plan の handoff（ADR-051）、`require_tools` のエラーに「cut.py has no --accurate」が出る。同じ job の別 package の候補（例 `video-editing/cut`）はそのまま選べる。`package_availability` の usable_tools も capability が欠けた tool を数えない。`supports()` は変えない（False にすると理由が「adapter が無い」に潰れるため）。最後の防壁として、`FfmpegSkillAdapter.build_argv` は unavailable な tool を理由付きの ToolError で拒否し、argparse まで届かせない。
  - ADR-047 の fatal / non-fatal の分け方をこの Skill に当てはめると、fatal は contract_version の major・skill id・catalog に載る tool / flag / positional / switch の arity、それ以外（説明文、新しい tool や flag、diagnostics 等）は non-fatal で見ない。ffmpeg-skill には pinned contract ファイルを置かない: catalog そのものが pin であり、contract は release ごとに大きく伸びる（42 tool）ので、全体の drift は意味のある信号にならない。
- 検証: unit（`FfmpegSkillContractCatalogTests`）: 偽の contract で flag 改名 → その tool だけ unavailable・理由付き、`--crf`/`--quality` のどちらも無い export、switch の arity 反転、tool の削除、positional の改名、contract_version 2.0 / 0.9 / 欠落 / 別 skill id → refused、doctor の `usable: no` は fix 付きで止め `unknown` は止めない、`_contract.py` の無い checkout は unchecked。`_contract.py` を持つ偽 checkout を locate し、resolver → select_tool の理由 → usable_tools → adapter の ToolError まで通す。integration（CI は ffmpeg-skill の main を clone）: `FfmpegSkillContractTests.test_contract_publishes_every_catalog_flag` が main の contract で contract_version 1.x と catalog の全 flag を確かめ、Service の capability が contract の判定と一致すること。
- 対象外: contract から catalog を生成すること（catalog は agent が使うと決めた flag の宣言であり、自動では増やさない）。`offers_flag`（`--help` 読み）を contract 読みに置き換えること。contract の `output_schema` と catalog の `result_keys` の照合。
- 追記（同 PR の別 commit、qc-skill #22）: qc-skill の contract は `version` を定数 0.1.0 ではなく pyproject の値（main で 0.2.2）で報告するようになった。それ以外の contract は ADR-055 の pin と同一（sibling checkout の live contract と比べ、差は `version` だけ）。`SUPPORTED_SKILL_VERSIONS` を `("0.1.", "0.2.")` に広げ、pin を `contract_0.2.2.json`（version を main の 0.2.2 にした live contract）に作り直し、fake と test の version 文字列を合わせた。`test_version_gates.test_qc_release_versions` が 0.1.x / 0.2.x を受け 0.3.0 / 1.0.0 を拒否することを固定する。

## ADR-057 ecosystem.json が他の package に割り当てた仕事を phase 2 の SkillSpec として宣言し、`job.<skill>=true` で頼まれた時は BLOCKED の step と、package・repository・インストール方法を名指しする handoff を出す（ECOSYSTEM_ROADMAP step 1、2026-10-30）
- 事実: ADR-051 の handoff は「tool を選べない step」しか報告できず、step は SkillSpec がある仕事からしか作られない。ecosystem.json（AI-video-production-OS、schema_version 2）の 33 component のうち、agent に adapter も SkillSpec も無い仕事（取込、声の分離、吹替、BGM・効果音、話者識別、顔・文字・物体検出、スライド同期、配信先アップロード、静止画編集、3D、Remotion、HyperFrames、生成文書の検証、ディスク作成）は、plan で頼む手段も、誰が持っているかを名指しする手段も無かった。また handoff の repository 名は package id に `-skill` を足して作っていたので、`bdmvkit` などは存在しない `bdmvkit-skill` になり、plugin でない component（voice-enhance・dubbing・sound-design・publish・ディスク系）にも `/plugin install` を出していた。ディスク作成は ecosystem.json で 4 つの repository に分かれている: Blu-ray（bdmvkit）、DVD-Video（vtskit）、UDF ディスクイメージ（udfkit）、DVD の line-21 字幕 CEA-608（dvdcc）。oncemore は Mac アプリ（「ディスク作成アプリ(Mac)」）で、agent が呼ぶ Skill ではない。voice-enhance / dubbing / sound-design / publish の各 repository は main で README と roadmap だけの scaffold で、インストールできる package が無い。ingest-skill は ecosystem.json では scaffold だが、offload / verify / inventory は出荷済み（README）。
- 決定:

## ADR-059 URL 素材の取得を ingest-skill（`ingest fetch`）に渡す。agent は yt-dlp を直接呼ばず、ingest-skill の報告から IngestRecord を作り、ingest-skill が無ければ ADR-051 の handoff で名指しする（2026-10-30）

## ADR-060 黒帯（レターボックス / ピラーボックス）を analysis kind `crop_rectangle` として測り、サンプルした区間で安定した矩形だけを `video.crop` の CONFIRM decision として提案する。承認されるまで切らない（ECOSYSTEM_ROADMAP step 7、2026-10-30）
- 事実: ADR-046 で ffmpeg-skill `cropdetect.py` を measurement skill `cropdetect_analysis`（tool `ffmpeg-skill/cropdetect`）として登録したが、Observation / AnalysisKind への統合と、測定から `video.crop` を提案する Decision は follow-up として残していた。`video.crop`（`edit.crop` = 利用者が明示した矩形 → `video_crop` step → `ffmpeg-skill/crop`）は既にある。ffmpeg-skill main（2.22.1）の `cropdetect.py` は `--seconds`（既定 10）の映像を `--samples`（既定 5）個の window に分けてファイル全体に散らし、window ごとに cropdetect filter（`reset=1`、frame ごとの読み）を走らせ、全 window の読みの最頻値の矩形を `crop`、それに一致した読みの割合を `confidence`、`windows` / `windows_failed`（decode できなかった window）と `source_width` / `source_height` を返す。読みが一つも無い（全面黒など）と `crop: null`。開始時刻を指定する flag は無い（区間を選ぶのは tool）。`--round` の既定は 16 で、幅・高さを 16 の倍数に切り下げる（1920x806 の画は 1920x800 になり、絵を最大 14 px 削る）。`--round 2` なら偶数に丸めた実測値（同じ素材で 1920x806）。`crop.py` は幅・高さが偶数でないと拒否し、丸めない。`_contract.py --json --static` の cropdetect の input_schema に `--seconds` / `--samples` / `--limit` / `--round` があり、catalog の flag（`round_to` → `--round`）と一致する（ADR-056 の照合対象）。
- 決定（測定）:
  - analysis kind `crop_rectangle`（skill `cropdetect_analysis`、audio 不要）を追加する。FULL / TARGETED の既定には入れず、`plan --kind crop_rectangle`（MCP の `kinds`）で明示的に頼んだ時だけ測る（`sync` と同じ）。video stream の無い入力は SKIPPED。
  - tool に渡すのは agent が固定した `CROP_TOOL_ARGS` = `--seconds 10 --samples 5 --round 2` だけ（`--limit` は tool の既定）。これが Observation の `parameters` と cache key になる。`--round 2` にするのは、絵を削らずに crop.py が受ける偶数の矩形を得るため。
  - Observation（provenance OBSERVED、source `ffmpeg-skill/cropdetect@<version>`）の data は tool のキーのまま `source_width` / `source_height` / `crop{x, y, width, height}` / `confidence` / `windows` / `windows_failed`。file path と commands は入れない。`source_width` / `source_height` / `crop` キーが無い結果は ANALYSIS_INVALID_RESULT。Event は作らない（時間区間の事実ではない）。
- 決定（安定の規則、`agent/crop.py` の純関数 `stable_rectangle`）: 次をすべて満たす時だけ矩形を提案する。
  1. `crop` が報告されている（`null` は「読みが無い」であって「帯が無い」ではないが、どちらにしても提案しない）。
  2. decode できた window が 3 以上（`windows - windows_failed ≥ MIN_WINDOWS`）。
  3. `confidence ≥ 0.9`（`MIN_CONFIDENCE`）。confidence は全 window の frame ごとの読みの一致率なので、5 window のうち 1 つ（全体の約 20%）が別の矩形を読んだだけで 0.8 になり提案しない。区間によって帯が違う素材（途中だけレターボックス、暗いシーンで読みが揺れる）は「安定していない」として扱う。
  4. 偶数への丸めは内側へ: 左・上の辺は次の偶数へ、右・下の辺は前の偶数へ動かす（`even_inward`）。矩形は大きくならず、測定が帯と呼んだ画素を含まない。丸めた後に frame の内側にあり、幅・高さとも 16 px 以上（validator と crop.py の下限）。実測（yuv420p、`--round 2`）では cropdetect が返す offset・寸法はすでに偶数で、丸めは何もしない（他の pixel format や round 値への備え）。
  5. 帯が幅か高さの 1% 以上を削る（`MIN_BAR_FRACTION`）。それ未満の縁の数 px はノイズ・アナログ由来の縁として提案しない。

- 決定（提案しない場面）: 明示 `edit.crop`（利用者の矩形が優先。測定は Observation として残る）、複数入力の programme（concat / switch / grid / takes。1 入力の帯は programme を表さない）、audio production path（絵を納品しない）。いずれも測定は残し、decision は作らない。

## ADR-062 衛星 Skill がすでに提供しているものを配線する（第1部）: color-grading-skill の PRIMARY_CORRECTION の gamma / lift / gain / levels / curves と、video-editing-skill の TRIM（明示の in / out）と ROTATE。ROTATE / FREEZE / REVERSE は lowering も足す（ECOSYSTEM_ROADMAP step 6 の第1部、2026-10-30）

## ADR-063 衛星 Skill がすでに提供しているものを配線する（第2部）: audio-production-skill の MIX / NOISE_REDUCTION / DYNAMICS と、subtitle-skill の render `mode: "mux"`（ソフト字幕トラック）（ECOSYSTEM_ROADMAP step 6 の第2部、2026-10-30、PR #81）
- 事実（pin の確認）: audio-production-skill main（0.4.2）の `audio-production skill --json` と subtitle-skill main（0.2.0）の `subtitle-skill contract --json` は、agent の pin（`contract_0.4.2.json` / `contract_0.2.0.json`）と完全に一致した（再 pin 不要）。audio-production の contract は MIX（入力 2〜8、`levels` = 入力ごとの {gain_db -60〜60, mute}、長さは先頭入力 = amix duration=first）、NOISE_REDUCTION（`mode` enum fft・必須、`strength_db` 10〜60・必須・既定無し）、DYNAMICS（`gate` / `compressor` / `limiter` の 3 段、段ごとの field と値域、段の中で省いた field は ffmpeg の既定、少なくとも 1 段）を宣言し、adapter の lowering は以前から全 14 型を contract の parameter schema で検査して送れたが、planner はこの 3 つを作らなかった。MIX に ducking（sidechain）の parameter は pin にも main にも無い（ffmpeg-skill の audio.py には `--duck` があるが、audio-production の contract が出していない）。
- 事実（mux の持ち主）: ecosystem.json の所有表で字幕は subtitle-skill（字幕生成・検証 / 字幕焼き込み）、ffmpeg-skill は FFmpeg 実行。subtitle-skill の pin した contract は render に `mode`（`capabilities.render_modes` = burn / mux、`parameters.render` = mode / audio_stream）を宣言し、mux は ffmpeg-skill/caption `--mode mux` に委ねる。よって mux は subtitle-skill の render に `mode: "mux"` を渡して頼み、agent は ffmpeg-skill の caption を直接呼ばない（重複させない）。
- 決定（音）: requirement key は contract の parameter 名で足す（すべて `audio.production=true` の audio path 上、既存の audio.* と同じく switch 無しは曖昧として拒否）: `audio.mix`（bool）+ `audio.mix.levels`（入力順に dB の数・`mute`・{gain_db, mute} の list、または `"0,-12,mute"`）、`audio.noise_reduction.strength_db`（必須）+ `audio.noise_reduction.mode`（fft。contract 唯一の値で必須なので省略時も fft を送る）、`audio.dynamics.<gate|compressor|limiter>`（true = その段を既定値で）+ `audio.dynamics.<段>.<field>`（contract の field 名と値域そのまま、15 key）。値域は `agent/audio.py` の定数で持ち、テストが pin した contract と突き合わせる。新しい key は `REQUIREMENT_KEYS` から `_SWITCH_REQUIREMENT_KEYS` に入るので `--set` の検査と brief の許可 key（`BRIEF_REQUIREMENT_KEYS`）に自動で入る。approval key `audio.mix.approval` / `audio.noise_reduction.approval` / `audio.dynamics.approval`（既定 CONFIRM、それぞれ自分の明示 requirement で waive）。
- 決定（mix）: `audio.mix` は audio programme を作るもう一つの方法（`audio.concat` と排他、両方は planning で拒否）。decision `audio.mix`（TRANSFORM、risk MEDIUM、params inputs / levels）→ IR `audio.mix {asset: programme_audio, inputs, output, levels?, segments, timeline_duration}` → step `audio_mix` → MIX。入力は入力順、各入力は 0 秒から自分の時間軸のまま足され、長さは先頭入力の長さ（segments も同じ）。そのため mix する入力からは無音を切らない（切ると入力どうしの位置がずれる。テイクの pick と同じ扱いで silence の REMOVE decision を作らない）。BLOCK（推測しない）: 入力が 1 つ、9 つ以上、levels の数が入力数と違う、MIX capability が無い。先頭入力の mute は planning で拒否（Skill は先頭の生きている入力を長さの基準にするので contract の「先頭入力」とずれる）。出力の channel 数は先頭入力のもの（QA の期待値）。loudness の正規化は programme に 1 回（concat と同じ）。
- 決定（noise reduction / dynamics の順序）: 固定順を noise reduction → gain → channels → dynamics → fade in → fade out → loudness にした。ノイズは生の信号で推定し、compressor / limiter は gain と channel layout の後の信号に、フェードは compressor に持ち上げられない位置に、loudness は最後。1 入力でも mix / concat の programme でも同じ順で、IR の型 `audio.noise_reduction {mode, strength_db}` / `audio.dynamics {gate?, compressor?, limiter?}`、step `audio_noise_reduction` / `audio_dynamics`、compiler は contract の名前でそのまま渡す。
- 決定（strength_db を 20〜60 に狭める）: 実 Skill の integration で `strength_db: 12` が TOOL_ERROR になった。audio-production は ffmpeg-skill audio.py `--denoise-strength 12` を呼び、audio.py は `afftdn=nf=-12` を作るが、afftdn の nf は -80〜-20 しか受けない（ffmpeg 6.1 で確認）。contract（と audio.py の help）の 10〜60 のうち 10〜19.99 は実行できないので、agent は 20〜60 だけを受け、それ未満は planning で理由付きで拒否する（実行して失敗させない）。contract の値域は `NOISE_REDUCTION_CONTRACT_STRENGTH` として残し、テストがこの一点の狭めだけを許す。直すのは ffmpeg-skill（audio.py の値域か nf への写し方）で、ここでは回避しない。
- 決定（字幕 mux）: `subtitle.mode`（render の `mode` そのもの、burn | mux）を足す。`mux` は decision `subtitle.mux`（TRANSFORM、risk LOW、approval key `subtitle.mux.approval` 既定 CONFIRM、明示で waive）→ IR `captions.mux {asset, input, sidecar, output}`（`captions.burn` と同じ参照、同じ subject に両方は書けない）→ step `subtitle_mux`（tool `subtitle/render`）→ render の要求に `mode: "mux"`。`subtitle.mode=burn` は `subtitle.burn_in=true` と同じで、burn_in と食い違う組み合わせは planning で拒否。sidecar（srt / vtt）は従来どおり作り、render には cue を srt で送る（contract の render formats は srt だけ）。adapter は contract の `render_modes` に無い mode を送らず、Skill の response の `mode` が頼んだものと違えば成功と認めない。BLOCK: 中間物が無い（burn と同じく Skill は workspace 内の入力しか取らない）、納品先に platform preset がある。後者は実測による: ffmpeg-skill の export.py（youtube も copy も）は絵と音だけを書き出し mov_text の字幕トラックを落とす（loudness.py は `run_keeping_subtitles` で残す）。preset のある profile では mux したトラックが納品物に届かないので BLOCK にし、generic など preset の無い納品で使う。export に字幕ストリームを残させるのは ffmpeg-skill の仕事として引き渡す。QA は captions.mux のある subject の納品物で字幕ストリームを数え、0 なら FAIL（`subtitle_track`、incident `MISSING_SUBTITLE_TRACK`）。brief の規則の読み手は "soft subtitles" / "subtitle track" / 「ソフト字幕」「字幕トラック」を `subtitle.mode=mux` に読む（焼き込みと両方書かれていれば読まない）。mp4 の mov_text は 2 文字の言語タグ（"ja" など）を落とす（subtitle-skill の engine.py が記録している既知の挙動）が、ここでは言語タグを書き換えない。
- 検証: `tests/test_satellite_params.py` に 15 件（音 9・字幕 6、CI の unit job で既に実行されるファイル）: 値域・enum・arity が pin した contract と一致（MIX に ducking の parameter が無いことも）、requirement の語彙と拒否（parser と `--set` の検査の両方、未知の key `audio.noise_reduction` / `audio.dynamics.compressor.mix` / `audio.mix.duck`）、brief の許可 key、compiler の要求、fake Skill の pipeline（2 入力 mix → noise reduction → dynamics → normalize、入力は切られない、長さ 16 s = 先頭入力、provenance の args）、BLOCK（levels の数違い・1 入力・MIX capability 無し）、1 入力の順序（cut → noise reduction → gain → mono → dynamics）、改ざんした IR（schema と validator）、mux の decision / IR / step / 要求 / QA PASS、preset の BLOCK、途中でトラックを失えば QA FAIL、中間物無しの BLOCK、mode の違う response の拒否。evals 121（mix + noise reduction + dynamics + normalize の E2E）・122（levels の数違いは BLOCK）・123（mux の E2E、generic）・124（burn_in と mux は planning で拒否）・125（preset があれば mux は BLOCK）。integration（CI が各 main を clone）: `AudioProductionRealTests.test_mix_noise_reduction_dynamics_end_to_end`（本物の audio-production-skill で 16 s stereo + 5 s mono を mix し noise reduction・compressor・limiter、出力 16 s stereo、Skill が返した parameter）、`SubtitleMuxRealTests`（本物の subtitle-skill と ffmpeg-skill、認識だけ fake: 納品物に mov_text のトラックが残り QA PASS。export.py が youtube / copy で字幕ストリームを落とすことの実測と、そのときの BLOCK）。ローカルで ffmpeg-skill / audio-production-skill / subtitle-skill ほかの main を clone して通ることを確認した。
- 対象外（step 6 の残り）: motion-graphics の全 12 element、qc の delivery_package gate、FREEZE / REVERSE の requirement と planner。mix の入力ごとの処理（mix の前に片方だけ noise reduction する、など）、ducking（audio-production-skill の contract が出したら配線する）、render の `audio_stream`、preset のある納品での mux（ffmpeg-skill の export が字幕を残すようになったら BLOCK を外す。`SubtitleMuxRealTests` がそれを知らせる）。

## ADR-064 衛星 Skill がすでに提供しているものを配線する（第3部）: motion-graphics-skill の全 12 element と、その全 parameter。明示した配置は編集後の絵の大きさで確かめる（ECOSYSTEM_ROADMAP step 6 の第3部、2026-10-30）
- 事実（pin の確認）: motion-graphics-skill main（0.2.3）の `motion-graphics skill --json` は agent の pin（`contract_0.2.3.json`）と完全に一致した（再 pin 不要）。contract が出す element は 12: title / lower_third / text_overlay / image_overlay / video_overlay / bug / chapter / progress / countdown / sticker / hook / meme（shape は `unsupported_element_types`）。agent が出せたのは最初の 4 つ（ADR-031）で、その 4 つでも parameter の一部（title の text_color / primary_color、text_overlay の margin / font / font_size / font_color / border_* / box / box_color / opacity、image_overlay の margin / scale_width / opacity）は出せなかった。adapter は以前から contract の element schema で全 element を検査して送れた（video_overlay の `video_path` を除く）。

## ADR-065 QC gate に納品セットの検査（qc-skill kind `delivery_package`）を加える。deliverable とその字幕 sidecar・サムネイルをひとまとめに確かめ、その判定がセットの全員を gate する（ECOSYSTEM_ROADMAP step 6 の第4部、2026-10-30）
- 事実: qc-skill main（0.2.3）の contract は pin（`contract_0.2.3.json`）と完全に一致した。kinds に `delivery_package`（qc-skill ADR-010 / ADR-011）があり、`input` の代わりに `artifacts: [{artifact_id, artifact_type, path}]`（artifact_type は video / audio / subtitle / thumbnail / metadata / other）を取り、rule `delivery_package.artifacts[]`（required / min_size_bytes / expected_extension / 入れ子の video・audio・subtitle rule）と `cross_artifact`（dependencies / duration_consistency）で、存在・大きさ・拡張子・依存を検査する。provenance は member ごとに present と sha256 を返す。agent の qc adapter はこの kind を送れなかった（`input` が必須）。
- 決定（方針、ADR-032 の QA 方針に沿う）: QC gate は ADR-032 のとおり明示の opt-in（`qc=true`）のまま。新しい key は作らず、gate が有効で、deliverable にほかの成果物（字幕 sidecar かサムネイル）が付くとき、納品先ごとにそのセットを検査する（gate の既定の一部）。deliverable だけのときは各自の report で足りるので作らない。gate の外（`qc` 無し）では何もしない。
- 決定（plan / IR / compiler）: qc_steps が納品先ごとに step `step_qc_package_<target>_<subject>`（skill `qc_check`、params kind `delivery_package`、inputs = deliverable + sidecar + thumbnail、depends_on = その deliverable の qc step・sidecar の qc step・thumbnail の step）を足し、IR `qa.qc.packages[<subject>] = {targets, captions, thumbnail}` に書く（schema に追加、plan_hash に入る）。compiler は deliverable の実体（preset の無い納品先は subject の現在の media、ADR-032 と同じ）・sidecar・thumbnail を member にして `lower_qc_package`（qc/check、kind delivery_package、`artifacts` は artifact id で、cache_policy bypass、kind qa）を出す。rule（`agent/qc.py::package_rules`）は計画から書けることだけ: 全 member が required・空でない（min_size_bytes 1）・計画した拡張子（paths の拡張子）、sidecar と thumbnail は deliverable に依存。duration_consistency は使わない（qc-skill は字幕の長さを最後の cue の終わりとして測るので programme の長さと一致しない。sidecar と video の長さの比較は sidecar 自身の qc check が reference_video でしている、ADR-032）。validator は packages が subject 自身の CAPTIONS / THUMBNAIL output を指すこと、何か 1 つは付くこと、step があることを検査する。
- 決定（adapter の admission）: kind delivery_package は `artifacts`（{artifact_id, artifact_type, input}）だけを受け、`input` / companion との併用、contract の artifact_types に無い型、request に無い member を名指す rule、重複 id を拒否する。member の path は adapter が path policy で解決したものだけを送る（引数の path は従来どおり forbidden）。response は schema / skill / operation / kind / OBSERVED に加え、report.input.artifacts が送った順の id と一致し、provenance.artifacts の各 member が present で adapter が再計算した sha256 を持つときだけ admit する。違えば INVALID_RESULT（非 retryable）。
- 決定（QA / stage）: QA は member ごとに自分で sha256 を計算して再 admit し（`admit_package`）、`delivery_package` という QA item（layer qc、package の verdict）を全 member に、FAIL / WARN の check をそれが名指す member（cross-artifact の check は全員）に付ける。FAIL は incident `DELIVERY_SPEC_FAILURE`。artifact の stage は `qc_verdict_of`: deliverable と sidecar は自分の report と package の悪い方（自分の report が無ければ従来どおり FAIL）、サムネイルは package の verdict（以前は gate の外で常に candidate だった。package に入ると PASS で approved、FAIL で working）、timeline は従来どおり gate の外。セットのどれかが欠けたり違ったりすれば、自分の report が PASS の deliverable も working になり final に昇格できない。
- 検証: `tests/test_satellite_params.py::QcDeliveryPackageTests`（7 件）: rule と compile の形、fake Skill の pipeline で step・`qa.qc.packages`・要求の member 型・QA item・3 つとも approved・provenance、package FAIL で 3 つとも working と incident、fingerprint の違う report は admit されない（INVALID_RESULT）、deliverable だけ / gate 無しでは作らない、改ざんした packages の validator、adapter の拒否。既存テストの更新（3 本目の qc_check、サムネイルの stage が package で approved）: `tests/test_pipeline.py` s2〜s5、evals 89 / 90、integration の s3 / s5 と `_gate_coherent`。evals 129（セットの検査で 3 つとも approved）・130（package FAIL で 3 つとも working）。integration: `tests/test_adapter_qc.py::QcRealSkillTests.test_real_delivery_package`（本物の qc-skill で video + srt + png を agent の rule で検査して PASS・3 つの sha256 で admit、拡張子違いの thumbnail は FAIL でその member を名指す）、`IntegratedPipelineRealTests.test_s3_color_thumbnail_qc`（本物の thumbnail-skill と qc-skill で deliverable + サムネイルのセットが PASS、サムネイルが approved）。CI の integration job は qc-skill をすでに clone している。
- 対象外: duration_consistency（上記）、入れ子の video / audio / subtitle rule（各 member 自身の qc check と重なる）、timeline の package への同梱（qc-skill に timeline の型が無い。`other` で入れられるが計画した拡張子以上のことを言えない）、audio path の納品物（sidecar / thumbnail を作らない）。

## ADR-066 ingest-skill の検証付きカード offload を `media_offload` として実装する。カードのフォルダを入力にした plan は何も書かず、コピー先を明示させ、常に CONFIRM の decision を出す。承認後の render が `ingest offload` を 1 回実行し、コピーの inventory を新しい asset と OBSERVED observation にする（ECOSYSTEM_ROADMAP step 9 の ingest、ingest-skill の roadmap step 6、2026-10-30）
- 事実: ingest-skill main（0.1.0、#5〜#9）は `ingest offload <card> --dest A [--dest B ...] [--project P] [--hash sha256|xxh64] [--name-by folder|reel] [--reel R] [--dry-run] --json` を出荷している。カードの各 file を 1 回だけ読み、全 destination に並行して書き、それぞれを read-back で確かめ、既存の file は上書きしない（同じなら skip、違えば conflict）。destination ごとに `ingest-manifest.json`（`ingest/manifest@1`。そこで失敗した file は任意の `failed`）と ASC MHL の generation（`ascmhl/`）を書く。報告は `ingest/offload-report@1`（exit 0 ok、exit 3 は `ok: false` の同じ報告、exit 2 は `{"ok": false, "error": {code, message}}` で何も書かない）。1 つの drive の失敗はその drive のコピーだけを失わせ、ほかの drive は完全で検証済みのまま（ingest-skill ADR-004）。`--dry-run` は名前と大きさだけで何も書かない。`ingest inventory <folder> --json`（`ingest/inventory@2`）は読むだけで、収録ごとに 1 clip（XDCAM EX / AVCHD の分割収録は member を順に並べた 1 clip）、カメラの sidecar（NonRealTimeMeta の書かれていることだけ）、proxy・関連 file、reel / card id とその出所（operator / manifest / clip_names / fingerprint）、manifest の hash、ffprobe の事実（不明は null）を返す（ingest-skill ADR-003）。`ingest verify` は manifest と ASC MHL history に対して再 hash し、file ごとの失敗を code（FILE_MISSING / VERIFY_MISMATCH / INCOMPLETE）、期待値と実測値付きで返す。contract の errors は 17 code（SOURCE_NOT_FOUND / NO_DESTINATION / DUPLICATE_DESTINATION / DESTINATION_OVERLAPS_SOURCE / MANIFEST_NOT_FOUND / MANIFEST_INVALID / HASH_UNAVAILABLE / REEL_INVALID / URL_INVALID / NAME_INVALID / FETCH_UNAVAILABLE / FETCH_FAILED / INCOMPLETE / SOURCE_CHANGED / VERIFY_MISMATCH / FILE_MISSING / MHL_INVALID）。offload 報告の file ごとの失敗は status `failed` と文章の detail だけで、code は付かない（VERIFY_MISMATCH などの code が file に付くのは verify の報告）。agent 側は ADR-057 の phase 2 SkillSpec `media_ingest`（adapter 無し、`job.media_ingest=true` で handoff）だけで、ADR-059 は URL 取得（`ingest fetch`）だけを渡していた。
- 決定（adapter、`tools/ingest/`）: `IngestAdapter`（package `ingest`、tool `ingest/offload`（execution）・`ingest/inventory`・`ingest/verify`（measurement））。locate は ADR-059 と同じ `locate_ingest`（`VIDEO_AGENT_INGEST_DIR` の checkout、`~/.claude/skills/ingest-skill`・`./vendor`・隣の `ingest-skill`、最後に PATH の `ingest`）を `tools/ingest/locate.py` に移し、`agent/ingest.py` もそれを使う。argv は list で、shell は使わない。送る前に値を全部確かめる: card と destination は絶対 path、card はディレクトリ、destination は既にあるディレクトリ（マウントされていない drive の mount point を system disk に作らないため。ingest-skill は無ければ mkdir する）、同じ destination を 2 回・card と互いに含む destination を拒否、hash は pin した manifest の hash（sha256 / xxh64）、`--project` と `--reel` は ingest-skill の reel と同じ 1 つの folder 名の pattern（`-` で始まる値が option に読まれることも無い）、未知の引数と command 様の key を名前で拒否。報告は schema・dry_run・card・hash、そして destination ごとのコピー先（`<dest>/<project>/<card 名 か reel>`、頼んだ順）が計画どおりの時だけ受け取る（違えば INVALID_RESULT）。ok の報告でも manifest が無ければ受け取らない。copy は measurement にしない（`measure` で呼べるのは `dry_run: true` だけ）。executor の dry run は ingest-skill 自身の `--dry-run` になり、コピーしない。
- 決定（pin と drift、ADR-045 / ADR-047 / ADR-048 と同じ形）: ingest-skill main の `ingest contract --json` を `contract_0.1.0.json`（key を sort した 1 行、ensure_ascii なし）に pin。`check_contract` は skill_id・contract_version 1.x・version 0.1.x・3 tool の role / writes_media / mutates_input / network、execution（shell false、source_is_read_only、overwrites never、offload が network tool でないこと）、manifest（名前・schema・sha256）、inventory schema、17 code の存在を確かめ、外れたら ContractError（使わない）。`DRIFT_KEYS`（skill_id / version / contract_version / execution / manifest / asc_mhl / inventory / errors / capabilities / provides / not_provided / fetch と、tool ごとの role / writes_media / mutates_input / deterministic / network / argv）は全部報告する。`FATAL_DRIFT_KEYS` は skill_id / contract_version / manifest / inventory と、この adapter が使う 3 tool の role / writes_media / mutates_input / argv、加えて pin した error code の消失・exit code / retryable の変化。version（0.1.x の中）、新しい error code（agent は INCOMPLETE として code のまま扱う）、`ingest/fetch` の変更（URL 側が自分の schema を確かめる、ADR-059）、asc_mhl・capabilities など報告用の key は fatal にしない。capability `ingest` は resolver が他の Skill と同じ `_finishing_skill` で出す: fatal drift が無く doctor が ok / degraded の時 AVAILABLE（xxhash・ffprobe・yt-dlp が無いのは degraded。sha256 の offload には要らない）。
- 決定（エラーの写像、`ERROR_KINDS`）: ingest-skill の code はそのまま `error.code` に残し、agent の kind と recovery class を横に付ける。SOURCE_NOT_FOUND → SOURCE_MISSING / INPUT_MISSING、NO_DESTINATION・DUPLICATE_DESTINATION・DESTINATION_OVERLAPS_SOURCE・REEL_INVALID・NAME_INVALID・URL_INVALID → INVALID_REQUEST / INVALID_ARGS、HASH_UNAVAILABLE・FETCH_UNAVAILABLE → ENGINE_MISSING / TOOL_MISSING、SOURCE_CHANGED → SOURCE_CHANGED、VERIFY_MISMATCH → VERIFY_FAILED、MHL_INVALID → HISTORY_DAMAGED、MANIFEST_*・FILE_MISSING・FETCH_FAILED・INCOMPLETE と未知の code → INCOMPLETE（いずれも SKILL_ERROR）。exit 3 の `ok: false` 報告は code INCOMPLETE、kind は数と code だけから決める（文章は読まない）: mhl_failed か MHL_INVALID → HISTORY_DAMAGED、problems の code の kind、conflicts → CONFLICT、一部の destination だけ failed → PARTIAL（完全な destination は `details.complete`）、全部 failed → COPY_FAILED。重い順（KIND_ORDER）の先頭が `kind`、全部が `kinds`。`details.destinations` に destination ごとの数・manifest・ASC MHL generation・problems（code 付き）・warnings・その destination の manifest の `failed`（path と detail）・conflict の file を残し、exit code と ingest-skill の retryable も残す。timeout → TIMEOUT、JSON でない・受け取れない報告 → INVALID_RESULT / INVALID_OUTPUT。失敗した後、manifest のある不完全な destination には `ingest verify`（読むだけ）を走らせ、file ごとの code（VERIFY_MISMATCH → VERIFY_FAILED など、期待値・実測値付き）を `execution.offload.verify` に残す。コピーは自動で再実行しない（executor の max_attempts 1、IR の recovery_policy も 1）: 利用者の drive への書き込みをやり直すかは利用者が決める。直してから同じ plan を render すれば ingest-skill が続きをコピーする（同じ file は skip、上書きしない）。
- 決定（plan、`agent/offload.py` と `Service.plan_offload`）: 入力がディレクトリなら CLI の `plan` は offload の plan にする（カードのフォルダ 1 つだけ。brief / request は受けない）。requirement は `ingest.dest`（必須。JSON list、カンマ区切り、`--set ingest.dest=` の繰り返し）、`ingest.project`、`ingest.hash`、`ingest.name_by`、`ingest.reel` だけで、ほかの key は拒否。`ingest.dest` が無い、存在しない、相対 path などは ingest-skill を呼ぶ前に拒否（exit 2、何も書かない）。media の plan に `ingest.*` を付けても拒否し、`job.media_ingest` は「カードのフォルダを入力に `ingest.dest` を付ける」と言って拒否する。brief から読む key（ADR-061）には入れない（コピー先は path で、明示だけ）。plan は ingest-skill の `offload --dry-run`（file 数・bytes・reel・各 destination のコピー先）と card の `inventory`（構造・clip 数・分割収録・警告）だけを呼び、どちらも card asset（status `source_card`）の OBSERVED observation（`ingest_offload_plan` / `ingest_card_inventory`、source `ingest/<tool>@<version>`）にする。decision は TRANSFORM `ingest.offload`（USER、requirement と 2 つの observation が根拠、risk MEDIUM、approval は policy を見ずに CONFIRM 固定。basis の resolved も CONFIRM なので、IR を AUTO に書き換えると validator が拒否する、ADR-033）、step `step_media_offload`（skill `media_offload`、tool `ingest/offload`、params は source / destinations / project / hash / name_by / reel / roots）。destination が 1 つ、または 2 つが同じ volume（st_dev）なら「backup ではない」と警告に残す。ingest-skill が無い（使えない）時は step の tool が None で、BLOCK decision と ADR-051 の handoff（ingest-skill と `git clone … && pip install -e 'ingest-skill[fetch]'`・`/plugin install`）を出し、CLI は exit 3。IR は `project.kind = "offload"`（schema に追加）。offload の plan は revise しない（reject して plan し直す）。

## ADR-069 安全でない既定を3つ塞ぐ: MCP の値を CLI の option に読ませない、Skill をカレントディレクトリから探さず子プロセスに AI の資格情報を渡さない、AI に送る計測結果の path を basename にする（Trail of Bits の insecure-defaults / sharp-edges 監査、2026-10-31）
- 事実1（F1、Medium、MCP の argv option injection）: `mcp_server.tool_argv` は `["plan", *inputs, "--profile", v, ...]` のように client の値をそのまま argv に並べ、`--` で区切っていなかった。`inputs` の要素 `--output=/any/path.json` は CLI（`plan` の argparse）が option として読み、`save_ir` が Project IR をその path に書く（書き込める任意のファイルを上書きできる）。`--allow-source-dir` や `--no-hash` も同じ形で足せた。`brief` の text、`render`/`approve` などの project、`check` の output も同じ。option の値（`--profile v`）も、`-` で始まる値で argparse のエラーにできた。
- 事実2（F2、Medium、カレントディレクトリ基準の Skill 探索）: 明示の dir も `VIDEO_AGENT_*_DIR` も無いとき、`ffmpeg_skill/locate.py`・`media_analysis`・`transcription`・`video_editing`・`audio_production` の各 locate と `skill_process.locate_cli_skill`（subtitle / thumbnail / color-grading / motion-graphics / qc / ingest）は `~/.claude/skills/<name>` の次に `Path.cwd()/vendor/<name>` と `Path.cwd().parent/<name>` を探していた。展開した素材フォルダのような信頼できない場所で agent を起動すると、そこの `vendor/ffmpeg-skill/scripts/_contract.py` が実行される（`doctor` だけでも: locate 時に contract を読むため）。さらに Skill の子プロセス（`run_process_group`、contract / `--help` の読み取り、resolver の `ffmpeg -version` など）は agent の環境をそのまま継いでいて、`ANTHROPIC_API_KEY` なども渡っていた。
- 事実3（F3、Low、AI に送る絶対 path）: `build_request` は asset 名を basename にしていたが、observation の data（`safe_observation_summary` → `_scrub`）は media_probe の `file` などの絶対 path をそのまま残し、Anthropic provider の payload と MCP host の brief に入っていた（利用者が素材をどこに置いているか、ユーザー名を含む home の path が外に出る）。
- 決定1（MCP、`mcp_server.tool_argv`）: client の値は常にデータで、option にはならない。option は `--flag=value` の 1 語で書き（`-` で始まる値もその option の値）、位置引数（inputs / project / output / text）は最後に `--` の後ろに置く。`--set` / `--kind` / `--decision` / `--brief-requirements` / `--ai-recommendations` も同じ。argparse は subparser でも `--` の後ろを位置引数として読む（Python 3.9 / 3.11 / 3.12 / 3.13 で確認）。`-` で始まる値を拒否する方法は採らない: `-14 LUFS で` のような依頼文や `-` で始まる file 名を正当に使えなくなり、`--` で十分なため。
- 決定2（探索、新しい `tools/discovery.py`）: 推測の候補はカレントディレクトリに依存させない。`default_skill_dirs(name)` = `~/.claude/skills/<name>`、そして agent 自身が source checkout から動いている時（`Path(__file__)` から求めた `<root>/src/video_agent` で、`<root>` に `pyproject.toml` か `.git` がある）だけ `<root>/../<name>`。6 箇所の locate すべてがこれを使う。明示の dir と環境変数が権威的で推測に進まない規則（ADR-041 の決定2）、PATH 上のコンソールスクリプトへのフォールバックは変えない。エコシステムの開発レイアウト（全 Skill を agent の隣に clone する、README のセットアップ）と CI の integration job（`../<skill>` に clone し、さらに `VIDEO_AGENT_*_DIR` も設定）は今までどおり見つかり、しかも起動ディレクトリに依らなくなった。ADR-059 / ADR-066 の「`./vendor`・隣の `ingest-skill`」も同じくこの規則に置き換わる。
- 決定3（子プロセスの環境、`discovery.child_env`）: Skill と engine の子プロセスには `ANTHROPIC_*` と `OPENAI_*`（agent 自身が読む provider の資格情報。`providers/claude.py`、resolver の `AI_ENV`）を除いた環境を渡す。対象は `run_process_group`（ffmpeg-skill と、それを使う全 Skill adapter・`skill_process.invoke`）、`contract_check` の `_contract.py` / `doctor`、`FfmpegSkill.offers_flag` の `--help`、resolver の `_run`。MCP server が起動する `video-agent` 自身の子プロセスは agent なので資格情報を残す。どの姉妹 Skill もこれらの変数を読まないことを確認した。
- 決定4（AI への payload、`media/analysis.scrub_for_ai`）: AI に出る summary（observation の data、event の metadata、asset の technical facts）では、key が `file` / `path` / `dir` / `filename` か `*_path` / `*_dir` / `*_file`（複数形も）の値を basename にする（list はそれぞれ、dict は中を再帰的に）。leak 検査（`_scrub`）はそのまま掛かる。AI が提案した params の `_scrub`（decision_engine / brief）は対象外: そこは path を外に出す経路ではなく、意味を変えないため。
- 帰結（利用者に見える変化）: 作業ディレクトリの `./vendor/<skill>` や `../<skill>` に置いた checkout は、もう自動では見つからない。そう使っていた人は `VIDEO_AGENT_*_DIR`（または `--ffmpeg-skill-dir`）で指すか `~/.claude/skills/<name>` に置く。逆に、agent を source checkout から使っていれば、隣の Skill はどのディレクトリから起動しても見つかるようになった。wheel で入れた agent は隣を推測しない。Skill の子プロセスは provider の資格情報を見ない。MCP client が値に `--...` を書いても、それは file 名・依頼文として扱われる（存在しない入力として失敗する）。
- 検証: `tests/test_ai_host.py::McpServerTests::test_values_are_never_options`（plan / brief / render / check / approve / artifacts で、option に見える値が本物の CLI parser でも位置引数・option の値のまま）と `test_injected_option_does_not_write_outside`（server 経由で `--output=<外>` を inputs に入れても、存在しない入力として失敗しファイルは書かれない）。`tests/test_unit.py::CwdIndependentDiscoveryTests`（カレントディレクトリの `vendor/` と親に置いた 6 種の checkout を一つも拾わない、明示・環境変数・`~/.claude/skills` は効く、source checkout の隣は起動ディレクトリに依らず見つかる、`child_env` と `run_process_group` の子に provider の資格情報が無い）。`LocateAuthoritativeOverrideTests` は「隣」を agent の checkout の隣として（`source_checkout_root` を一時ディレクトリに向けて）検証し直した。subtitle / thumbnail / motion-graphics / qc の「何も見つからない」locate テストは、この環境（全 Skill が agent の隣にある）では以前から失敗していた（推測が本物の隣の checkout を拾う）ので、`source_checkout_root` と home を差し替えて環境に依らないようにした（変更前 4 件失敗 → 変更後 0 件）。`tests/test_ai_claude.py::test_payload_carries_no_absolute_paths`（録音する fake client で、payload に作業ディレクトリの path が無く media_probe の `file` は `talk.mp4`、`scrub_for_ai` の key と入れ子）。監査の再現 3 本（`plan` の injection で外にファイルが書かれる / 信頼できないフォルダで `doctor` が `vendor/ffmpeg-skill` のコードを実行する / Anthropic への payload に素材の絶対 path）が変更前は再現し、変更後は再現しない。
